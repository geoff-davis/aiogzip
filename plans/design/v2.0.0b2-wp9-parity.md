# WP9 design: hot-path parity, codec guidance and optional cleanup

Plan §13, gate G13: *named parity matrices cover retained hot-path
duplication; private cleanup is justified.* WP9 keeps tested, measured
duplication where removing it would add cost or change observable ordering.
It adds tests, comments, a guide warning and a contributor map, and makes
at most two small production changes: one dead-branch removal and one cast
removal. The comparison reference is C0 (`b074bdc`).

## Parity matrices (§13.1)

Each matrix is one parametrized test module. A scenario table is the
parameter set, and each path is an adapter with the same signature. The
modules are new; existing tests that cover a cell stay and are not duplicated
or moved.

### `tests/test_parity_operation.py` (D1)

Adapters: `public` drives `next()`; `raw` drives `_advance_raw()` and keeps
bytes and progress events separately. The comparison is the projected public
byte stream and the final state: active token, `_unusable`, `_discarded`,
`finished`, the size counters and member records. Raw progress events are
checked in a separate raw-only test. Advancement counts are not compared,
because public `next()` deliberately hides progress events.

Scenarios: output; private progress (decoder no-output steps); no-output work
(empty encoder feed); completion; failure before output and after output
(fake engine); reentrant advancement; a non-active token (an operation
superseded after discard and a new codec, or a stale reference); `close()`
before, during and after exhaustion; `discard()` with a retained iterator;
advancing an invalidated retained iterator; and release ordering (the token
is cleared before success or failure becomes visible, and `_release_state`
runs on failure).

### `tests/test_parity_encoder_feed.py` (D2)

Adapters: `public` calls `feed(data)`; `private` calls
`_feed_snapshot(_snapshot_bytes_input(data))`, as the file writer does after
its own snapshot.

First the matrix characterizes precedence. `feed()` checks, in order: active
operation, unusable, finished, unstarted, input type, strict size.
`_feed_snapshot` runs the same state checks in the same order, after a
caller-side snapshot. Each pair of simultaneous violations is asserted for
the public path, so a future refactor that delegated `feed()` as
`snapshot → _feed_snapshot` would fail. For example, an active operation
plus a `bytearray` must raise `RuntimeError`, not `TypeError`.

Scenarios: active, unusable, unstarted and finished preconditions; the strict
size boundary at exactly `0xFFFFFFFF` and one byte over, with nothing
reserved after the error; exact `bytes` passed through with no copy
(identity); a hostile `bytes` subclass whose `__bytes__`, `__len__`,
`__iter__` and `__getitem__` raise is snapshotted without calling them;
`bytearray`, `memoryview` and `str` rejected by the public path; and counter
timing. `input_size` and `crc32` are unchanged when the call returns and
advance only when the operation advances, on both paths.

### `tests/test_parity_binary_write.py` (D3)

Adapters: `inline` calls `write(data)`. `reserved` is a direct internal
adapter that runs the same public-state validation and snapshot as `write()`
(`_coerce_byteslike`), then `with file._write_call as encoder: return await
file._write_reserved(payload, encoder)`. It isolates the reservation from
`writelines()`, whose batching skips the codec entirely for empty input and
adds iteration unrelated to the reservation. Public `writelines()` keeps its
own existing coverage. Both adapters run against a recording sink, and both
return the payload length.

Scenarios: success; an empty write, instrumented to show each adapter drives
exactly one `_feed_snapshot` operation; a mutable `bytearray` mutated after
the call returns, showing the compressed member holds the call-time
snapshot; a partial-progress sink; a zero-progress
sink and an invalid count; a codec failure (fake engine) and a sink failure;
cancellation, repeated twice, during a sink write; close and context-exit
abort during an active call; overlap rejected with `ConcurrentOperationError`;
a completion waiter released on every exit; and position publication. In
every scenario, both paths must leave the same sink bytes, position,
`_write_broken`, encoder state (`discarded`, active token) and exception
type. The plan's invariants are asserted in the matrix:

- each successful call snapshots its input and drives its own operation;
- the operation's output reaches the sink within the same call;
- position is published only after every sink write succeeds;
- a failure surfaces in the same call, not a later write, flush or close;
- nothing is buffered across calls.

### `tests/test_parity_text_inline.py` (T1–T5)

Each inline path is compared with its reference path, over the scenarios
that apply to it:

| Path | Comparison | Scenarios |
| --- | --- | --- |
| T1 | `write(s)` vs `writelines([s])`: identical decompressed bytes, encoder state after failure, position | empty; every `newline` mode; multibyte encodings and an encoder that keeps state; sink failure (encoder state rolled back); cancellation; close and overlap |
| T2 | Origin after an inline refill vs `_capture_buffer_origin()` on the same state | refill at an empty buffer across `newline` modes, UTF-8 splits and UTF-16; the pending CR and newline mask are captured |
| T3 | `read(n)` or `read()` vs the same text assembled by `readline()` | chunk-boundary multibyte splits; trailing CR at EOF in each mode; validation salvage; source error and rollback |
| T4 | `async for` vs a `readline()` loop: the same lines and `tell()` cookies | each fast-line `newline` mode; empty file; no final newline; salvage then terminal; cancellation during refill; close during iteration; overlap |
| T5 | `readline(limit)` inline vs `_take_buffered_line(limit)` on the same state | limit inside, at and beyond a terminator; CRLF across the limit; a limit equal to the buffered length |

### Production comments and the map

Each duplicated site gets one comment line, `Parity: tests/<module>`, beside
its existing why-comment. The inventory table above, without the Id column,
becomes a short "Hot-path duplication map" section in `docs/contributing.md`,
next to the existing performance-check guidance, so contributors find why
each duplicate exists and which benchmark constrains it.

## Last yielded bytes are not completion (§13.2)

New tests in `tests/test_codec_encoder.py`, one per collection style:

- **Counted `next()`:** for a `finish()` operation, pull chunks until the
  collected bytes decompress as a valid member. Then assert `finished is
  False`, that the operation still owns the encoder (another state-changing
  call raises `RuntimeError("... has an active operation")`), and that the
  next `next()` raises `StopIteration`, after which `finished is True`.
- **Early `break`** from a `for` loop after the trailer bytes: the same
  not-finished, still-reserved state. Then exhaust and confirm completion.
- **`itertools.islice()`** to the known chunk count: the same.
- **Complete `for` exhaustion** and **`b"".join(operation)`:** complete.
- **Early `close()`** after the trailer bytes, before `StopIteration`: the
  existing abandonment rule applies. The encoder is unusable, `finished`
  stays False, and the next call raises `OSError`.

Operations are constructed and exhausted one at a time; no example holds two.

`docs/codec.md` gains a warning in "Lazy operations and ownership": a chunk
that completes a valid gzip byte sequence does not release the operation.
Always exhaust it, or close it explicitly and accept the documented unusable
codec. This is frozen behavior, not a defect to fix with finalizers. The
counter-timing distinction is already documented in "Counters" and stays as
is. `consumed_size` is not added. The G13 record notes the collection-style
evidence for any future additive helper.

## Conditional dead-branch removal (§13.3)

In `AsyncGzipBinaryFile._decompress_next`, the underlying-EOF branch drives
`decoder.finish()` with a plain synchronous `for` loop. There is no `await`,
executor hop or delivery boundary between `try` and the loop's end, so
ordinary task cancellation cannot be delivered there, and the inner
`except asyncio.CancelledError` is unreachable. The plan names this branch;
it is removed, with a comment naming the live cancellation boundaries: the
source read before it (`_read_compressed_chunk`) and the feed path's driver.

The feed path's `except asyncio.CancelledError` is live, because the driver
awaits the executor and cooperative checkpoints, and it is kept.

Behavior change: none for supported engines or ordinary task cancellation.
The defensive, private case does change: a `CancelledError` raised
synchronously by the codec itself, which no supported engine does, would now
propagate without poisoning the reader, as `KeyboardInterrupt` already does
from that loop.

Validation runs the actual preceding-read, worker, context-exit and repeated
cancellation suites on both engines:

- `test_source_read_settlement.py` and `test_native_work_settlement.py`;
- `test_b2_native_io.py`;
- `test_read_health_transitions.py`, `test_file_lifecycle.py` and
  `test_text_bridge.py`, which hold the context-exit abort tests.

## Optional private cleanup (§13.4)

- **`_reserve() -> _Operation`: adopt.** `_Operation` structurally satisfies
  `_AsyncDrivableOperation`, so `_feed_snapshot` returns `self._reserve(...)`
  without `cast`, which also removes one runtime `cast()` call from the D2 hot
  path. Public methods keep returning `CodecOperation`. The casts in
  `_streaming.py`, `_inspection.py` and `_binary.py` cast results of public
  methods typed `CodecOperation`, so they stay. Both type checkers and
  `test_public_api_typing.py` must pass, and the b1 runtime manifest
  (`tests/data/public_api_2_0.json`, checked by
  `test_public_api_contract.py`) must stay byte-identical.
- **Executor `workload` argument: leave unchanged.** The WP1
  [native-settlement design](v2.0.0b2-native-settlement.md) documents that the
  executor invocation retains the bound operation and its workload until
  native settlement. The argument is that documented retention, and no
  benefit is claimed for removing it.
- **Warning helper: decline.** The fast-compress fallback warning has two
  `stacklevel=2` sites (the encoder and binary constructors), and streaming
  re-emits it at `stacklevel=3`. A helper adds a frame, so every stack level
  would change. The plan's preservation list (category, message, count,
  filtering, timing, stack location) buys nothing measurable here.

## Benchmarks

WP9's production changes are a cold-path removal, one `cast()` call removed
from `_feed_snapshot`, and comments. One method-A window, `io,micro,
regressions` against C0, on both engines, confirms no hot path moved. It is
registered and reviewed like WP8's.

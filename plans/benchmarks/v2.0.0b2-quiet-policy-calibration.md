# Quiet-policy calibration: September 27

The proposed one-core foreign-CPU ceiling is **not qualified** by this experiment.
No production runner policy was changed and no new overnight run was scheduled.
G06, G07, G08 and G17 remain open.

## Experiment

The maintainer authorized testing a one-core ceiling while initially retaining
the 0.5 load1/load5 start limits and 120-second quiet period. The criterion was
predeclared before capture: each throughput case's maximum/minimum across four
capture minima must differ by at most 3%. Latency rows were retained but excluded
from this throughput decision.

The original overnight run deferred all work: every one of its 24 samples exceeded
0.25 foreign cores. The new trial also waited roughly twelve minutes because the
unchanged load threshold repeatedly reset its quiet period. It eventually passed
120 quiet seconds, starting at load averages 0.228/0.415/0.391. CPU 0 was pinned;
its SMT sibling is CPU 16. No unrelated process was stopped or moved.

Eight captures ran in engine order stdlib, zlib-ng, stdlib, zlib-ng, zlib-ng,
stdlib, zlib-ng, stdlib. Every capture used seven samples per case, the same
4 MiB workloads, the same copied Python environment and clean source/harness
16af1dc5aebe65a327165e059768566455c019eb. The measurement harness hash is
`4e011c32fef1c498079fc0e76030513d2b5c399d45823adb8477b721fe532e59`.
Imports, engine selection, fixture hashes and affinity were verified in the
captures. The scratch orchestration script is archived byte-for-byte and its
hash appears in the status record; it was not a committed qualification runner.

A dedicated systemd service accounted for its own CPU and exited children using
cgroup counters. All five-second foreign-CPU samples stayed below one core
(observed range including preflight: 0.338–0.996). As with the existing runner,
load limits applied before starting; during captures the CPU monitor excluded the
benchmark service's own work. Timing comparisons ran sequentially, not concurrently.

## Results

| Engine | Cases within 3% | Largest minimum-time spread |
| --- | ---: | ---: |
| stdlib | 12 of 16 | 5.10% |
| zlib-ng | 10 of 16 | 5.59% |

The largest spread was random-data zlib-ng decode with 64 KiB items: approximately
0.413–0.436 ms. However, this is not solely a sub-millisecond phenomenon: stdlib
random-data decode with 64-byte items ranged from 218.786 to 227.450 ms, a 3.96%
spread. Ten of 32 cases exceeded the predeclared criterion.

These are identical-code comparisons, not candidate regressions. This experiment
neither proves that background CPU caused the drift nor establishes that 0.25
cores would have eliminated it. Clock/thermal state, warmup and scheduling effects
were not independently controlled. The result is insufficient to adopt one core
as a qualification rule merely because the run can now start.

A follow-up should control warmup and lengthen short timing observations, then
repeat the predeclared same-code stability check. The longer drifting case also
needs attention; increasing duration alone cannot be assumed to fix it. Keep
raw measurements and baseline drift visible rather than retrying until a favorable
capture appears. Any further change to the load limits is a separate policy change.

Several spreads decrease steadily with capture order, including stdlib's 64-byte
random decode (227.450 → 223.293 → 221.817 → 218.786 ms). This makes warmup/clock
state worth investigating, without establishing a cause. The scratch controller's
900-second budget covered both preflight and captures; all eight completed around
815 seconds, after roughly 85 seconds of measurement-process execution. Future
calibration should budget waiting and measurement separately so a late start is
not incorrectly labelled interference when that combined budget expires.

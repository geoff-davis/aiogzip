- **Worktrees.** `run.sh` creates fresh detached worktrees for A, B and the
  runner. A and B are separate even when they share a commit. It verifies
  each commit and a clean tree, and requires the venv's `uv.lock` to equal
  the runner's.
- **Interpreter.** Every step runs the repository venv's interpreter
  directly, without `uv run`, so nothing re-syncs the venv mid-window.
- **CPU and quiet gate.** Every step is pinned to CPU 13. The WP9 quiet gate
  (`quiet_gate.py`, unchanged apart from its docstring) must see 120 s at
  2.5 foreign cores or fewer before a window starts, and a monitor samples
  foreign CPU every 5 s throughout.
- **Captures.** For each engine (stdlib, then zlib-ng), eight captures run
  in ABBA ABBA order. Each capture runs two steps:
  1. `run_benchmarks.py --category io,micro,concurrency,memory,regressions,read_health,text_origin --repeat 5 --regression-profile quick --regression-mode throughput`
  2. `bench_a3_regressions.py --categories writes --repeat 5` with the
     default sizes (10 B, 100 B, 1 KiB and 4, 16, 64 and 256 KiB) and all
     four write methods.
- **Structural steps.** These run after the ABBA loop in the C0 and WP0
  windows. Each step runs once per side and engine: A then B on stdlib, and
  B then A on zlib-ng. `measure_b2_partial_read.py` runs on stdlib only.
- **Units.** Each window runs as a systemd user unit started manually, as in
  WP8 and WP9. `RuntimeMaxSec` is set from the preflight durations below.

## Statistics and decision rule

`summarize.py` refuses any window in which:

- a capture is missing, incomplete, failed or mislabeled;
- a commit, the runner commit, the engine or the dirty state is wrong;
- the benchmark sets differ between captures;
- a write result is not `ok` with five samples;
- foreign-CPU samples fail to cover any capture or structural step
  continuously;
- foreign CPU exceeds 2.5 cores during any capture or step.

A refused window is rerun whole. The candidate is never rerun alone.

The primary statistic is each benchmark's minimum of the four capture medians
on each side, as in CLAUDE.md method A. The four adjacent A/B pair deltas are
reported alongside it.

Plan §15.1 policy applies to every runner row and write row of the C0 and WP0
windows:

| Slowdown (B against A, by minimum) | Required action |
| --- | --- |
| 5% or less | None |
| More than 5% | Investigation and a recorded disposition |
| More than 10% and attributable to the candidate | Blocks by default |

Adjacent pair deltas inform stability but do not decide eligibility.

**A/A use.** The A/A window reports each row's delta and the largest absolute
delta per engine. A final-window row above 5% is still investigated even if
its A/A row was also above 5%. The A/A result is evidence within that
investigation, not a waiver.

The `memory` category records an RSS increase per capture. It is reported
per capture and judged with the G07 resource rows, not by percentage.

## Preflight (needs authorization; not evidence)

Two things are unknown before a window runs:

- **Durations.** The full category set and the write sizes have never run
  together, so `RuntimeMaxSec` cannot be set from records alone.
- **Compatibility with the WP0 baseline.** `read_health` and `text_origin`
  postdate `dc8950c`. They use only the public API, but they have never run
  against it.

The proposed preflight is one functional pass per root (C0, `dc8950c` and
the current head) on stdlib only, with `--repeat 1`, one write repeat and
every structural step once. It runs unpinned, its output goes to a scratch
directory, and it is never cited as timing evidence. It reports per-step
durations and any step that fails on a root.

If a category fails on `dc8950c`, the WP0 window drops it through
`CATEGORIES_OVERRIDE`. That change is recorded here as an amendment for
review before the window runs.

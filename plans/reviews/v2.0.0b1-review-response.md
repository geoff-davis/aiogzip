## Corrective benchmark method

The first follow-up used three balanced process rounds per source tree and
engine, 21 timing samples per row, five allocation samples per row, CPU-0
affinity, and unchanged fixtures. Per-benchmark minima still moved together on
several byte-identical direct-codec rows, revealing process/source-tree bias.

The v2 targeted follow-up loaded exact a4 and clean diagnostic commit
`4a6fb9f81bfa370c2e8362534f05aadb3630317f` under distinct package aliases
in one process. It checked source provenance and the then-implemented engine
guard before one warm-up per side, then ran 50 A/B/B/A cycles, giving 100
samples per source tree and row with GC disabled. The output-bound case checks
byte count, digest, and maximum chunk on every sample; each header case checks
its output digest. Its output-bound result is +0.06% stdlib and +0.30%
zlib-ng.

The high-level header rows cannot be summarized as a resolved range. The v2
zlib-ng FCOMMENT minimum is -6.13%, while the 200-sample v3 original and
canonical-swapped minima are -0.83% and +2.00%. However, FCOMMENT quarter
medians fall about 25% through each record. Restricting v3 to its first 100
samples produces +13.22% in the original order and -7.94% raw (+8.62%
canonical) in the swap. FNAME also moves from +3.84% in v2 to -3.07% in v3,
a 6.90 percentage-point swing. Full-capture canonical FCOMMENT medians are
more stable at -1.75%, -0.67%, and -1.43%, but remain descriptive.

Consequently, the minimum-based targeted diagnostic is inconclusive at a 5%
threshold for these rows. The evidence does not clear them by choosing the
full-capture endpoint or by substituting medians. Instead, exact source
inspection establishes that a4 and b1 runtime implementation is byte-identical
apart from the version string, so the timing movement is not attributable to a
b1 runtime change. No performance improvement is claimed.

Both source trees were clean in the v2 records. Exact a4 reported
`v2.0.0a4`; the candidate reported `v2.0.0a4-12-g4a6fb9f`. The stdlib run
reported stdlib decompression and CRC on both sides, while the zlib-ng run
reported zlib-ng decompression and CRC on both sides.

The v3 records attest clean exact a4 and `daadbd0` source trees and record
zlib-ng decompression and CRC on both sides; they do not retain host OS
metadata. Their source orientation and reciprocal normalization formula are
now explicit. Commands reconstructed after capture are retained only as
non-contemporaneous reproduction aids, and timing samples are unchanged.

The shared runner and comparator behavior is covered by committed unit tests.
No unretained no-zlib guard run or 18-row smoke capture is cited as release
evidence. New captures store requested engine separately from the actual
stdlib-only environment override; retained main-harness captures require
`--allow-legacy`, which prints their provenance limitations.

The diagnostic is `benchmarks/investigate_b1_timing.py`; raw inputs and output
paths are listed in `plans/benchmarks/v2.0.0b1-candidate.md`.

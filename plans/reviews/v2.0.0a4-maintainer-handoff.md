## Required review and CI sequence

1. Push the review branch and open focused pull requests, or document why the
   existing reviewable commit groups are reviewed together.
2. Give an independent human reviewer the review packet and exact review
   commit. Require concrete findings and at least one example run.
3. Record reviewer name, date, scope, example command/result, findings,
   corrections, and explicit final approval in a new
   `plans/reviews/v2.0.0a4-independent-review.md`.
4. Run the existing `Python CI` workflow against the exact corrected
   candidate. Record run URL and every job result, including Linux Python
   3.11–3.14, Windows 3.12, macOS 3.12, zlib-ng, no-zlib-ng, and forced
   stdlib.
5. Address blocking findings in focused commits. Rerun affected local tests,
   benchmarks when relevant, full CI, and reviewer approval on the corrected
   commit.
6. Only then make the release-prep version and dated-changelog commit.

Do not use a current-success badge or an unrelated main-branch run as
candidate evidence. Record the exact commit and workflow run.

## Honest limitations

- The codec API remains provisional in a4.
- Arbitrary random access remains replay-based.
- AnyIO/Trio and indexed access remain deferred.
- Tiny individual writes remain slower than explicit bounded batching.
- The examples are application patterns, not turnkey frameworks.
- Decoded payload remains provisional until trailers and normal stream
  completion validate it.
- Development artifact hashes above will change during final release prep.

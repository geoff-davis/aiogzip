# aiogzip 2.0.0b1 benchmark candidate

> **Status:** local exact-a4 attribution disposition complete; hosted CI and
> exact-head review remain pending
>
> **Date:** 2026-08-31

## Provenance and method

The primary baseline is exact tag commit
`262d9a5a0eb5f84fc54432e968b845b182fd255c` (`v2.0.0a4`). The primary codec
candidate is clean commit `0534a64c92b1d6bca91c975582c60e68f99339f0`.
The codec baseline and candidate used the same regression harness, whose
SHA-256 is
`64c3c0e2431ac265b10736940bcddebb8c775f9e6cf6115dc3a26d21a3af6d27`.

The controlled a3 and a4-supplement recaptures compare the exact a4 checkout
with clean candidate commit `08f2517798d671cd8f3586cd1b6636a4a02f49fd`
under the same Python 3.12.12 environment and CPU-0 affinity. The only runtime
source difference between exact a4 and that candidate is
`aiogzip.__version__`; the intervening changes are tests, documentation,
metadata, CI, artifact tools, and benchmark progress output. The a3 matrix
uses 21 timing samples and one allocation sample. The supplement uses nine
samples. Fixtures, ordering, statistics, and thresholds were not changed.

Review of commit `fa507af021fd453287e80ee2668441aadf63021a` found that
single-process ordering noise and single-sample allocation bimodality were not
fully dispositioned in the first version of this record. The corrective
investigation retains those original records, adds three balanced
A/B/B/A-style process rounds per engine with 21 timing and five allocation
samples per row, and then uses a focused same-process A/B/B/A diagnostic with
100 samples per source tree. Per-benchmark minima are used for the focused
comparison, as required by `CLAUDE.md`; medians remain descriptive only.

Review of corrective commit `e412cc6a2ee76e080883332cfbd9988784ffcdeb`
found that the first focused diagnostic did not reject an unavailable requested
engine or dirty tracked source trees. The hardened diagnostic at clean commit
`4a6fb9f81bfa370c2e8362534f05aadb3630317f` performs those checks before
fixture construction, records exact commit and `git describe` identities plus
the active engines, and atomically checkpoints partial results. The hardened
v2 captures supersede the first focused captures for stdlib and remain
intermediate evidence for zlib-ng; both generations remain retained.

Review of commits `4a6fb9f81bfa370c2e8362534f05aadb3630317f` and
`5f53e9673003d8ea7327fb0a342ce3f16b2309ea` found that the v2 zlib-ng result
contained a same-source -6.13% swing and that the engine guarantee was weaker
than documented. Clean tooling commit
`daadbd081d015a893104f9c0a28aa29a5c7cd68a` validates every default engine
field, with the intentional macOS stdlib-CRC exception, and applies clean-tree,
engine, atomic-checkpoint, and comparison-parity guards to the shared release
harness. Two 200-sample-per-side zlib-ng v3 captures, including an order swap,
investigate the -6.13% observation below.

Review of evidence commit `cdfb4d7d87d144ea9f5b2989b3a3922f68ec8183`
showed that the zlib-ng high-level FCOMMENT row is non-stationary and that the
minimum statistic merely relocates the crossing as the row warms. Tooling commit
`ab9c977` records orientation and commands for future captures, uses meaningful
warm-up cycles, exposes temporal slices, and restores explicit comparator
access to retained pre-hardening records. This correction does not perform a
fourth recapture or claim that the targeted diagnostic established a 5% noise
floor.

Review of tooling commit `ab9c977` and evidence commit `1f3c6a2` found that the
documented no-source workflow remained incomparable and that the targeted
reader did not enforce its producer provenance, orientation, or platform
contract. Tooling commit `e26264b` makes comparable workflows use clean
`--source-root` captures, verifies engine requests even without source
attestation, and requires `--allow-legacy` for these post-capture-annotated v3
records. It also derives orientation from the retained source versions before
printing any results.

Every harness prints `START <benchmark name>` before entering a timed row.
This makes a long-running case distinguishable from a stalled process without
placing output inside the measured region.

Policy is applied per comparable named row: at most 5% slower passes, more
than 5% requires investigation, and more than 10% blocks release. Negative
percentages below mean the candidate was faster.

### Investigated codec threshold crossing

The stdlib `direct output bound 262144 bytes` row moved from 96.44 us to
101.87 us by median, a 5.63% or 5.43 us slowdown. Minimum-to-minimum was also
+5.60%; the three fastest candidate samples were +5.60%, +6.98%, and +7.35%
above the baseline minimum. The original five-sample capture therefore does
not support the earlier claim that ordinary distribution overlap was
sufficient to dismiss the result.

The focused diagnostic loaded exact a4 and b1 into the same process under
distinct package aliases, disabled GC during measurement, and used A/B/B/A
ordering. The v2, 100-sample captures measured the output-bound row at +0.06%
for stdlib and +0.30% for zlib-ng; the v3, 200-sample zlib-ng captures measured
+0.19% in original order and -0.06% after canonical orientation of the swap.
For this output-bound case, every sample checks byte count, output digest, and
maximum output chunk; its fixture reference digest is computed once before
timing. The eight header cases check the output digest on every sample.

This stable output-bound follow-up is consistent with process noise in the
original five-sample +5.60% minimum result. It is not generalized to the
non-stationary zlib-ng FCOMMENT row discussed below. The release attribution
rests on the verified fact that exact a4 and b1 have byte-identical runtime
implementation for this operation, not on a claim that every targeted row is
measurable to 5% by minimum.

## High-level, member, and write matrix

The retained controlled captures contained all of these threshold crossings:

- first stdlib pair: complete-FNAME 64 MiB high-level +18.94% and direct
  +10.69% by median;
- first zlib-ng pair: direct incomplete-FCOMMENT 32 MiB +5.27% by median and
  +5.01% by minimum;
- reverse-order stdlib recapture: complete-FCOMMENT 32 MiB high-level +5.18%
  and complete-FNAME 64 MiB direct +9.19% by median.

The reverse-order minimum statistic was +10.11% for the high-level FNAME row
and +9.84% for the direct row. That capture therefore crossed the 10% blocker;
its median could not be used to waive the result. Release evidence remained
blocked while the prescribed interleaved and targeted investigations ran.

Three balanced process-level rounds per engine retained the same fixtures,
21 timing samples, and CPU affinity. Their per-row minimum comparison still
showed several unchanged direct-codec rows 5.19% to 6.84% slower for stdlib and
5.84% to 8.76% slower for zlib-ng. That broad movement across byte-identical
direct paths demonstrated a remaining process/source-tree bias rather than
isolating any candidate operation.

Those records also contain a +8.08% stdlib minimum-duration change for
`high-level fname-32MiB-incomplete memory`, from 4.05095 ms to 4.37820 ms;
the zlib-ng comparison is -1.71%. This row runs under `tracemalloc` and its
duration is explicitly informational rather than a wall-time claim. It does
not participate in the timing thresholds, but is enumerated here for
completeness. Its gated resource metric is peak Python allocation, dispositioned
by the repeated allocation evidence below.

The focused same-process diagnostic reduces process separation but does not
make every row stationary. Results must therefore remain separated by capture
generation, sample count, candidate commit, and orientation.

The zlib-ng FCOMMENT high-level samples drift materially: quarter medians fall
from about 3.9 ms to 2.9 ms in v2 and from 3.7 ms to 2.8 ms in v3. On v3's
first 100 samples, matching v2's sample count, the original-order minimum delta
is +13.22%; the swapped raw first-half delta is -7.94% (+8.62% canonically).
The v2 stdlib FCOMMENT capture is materially steadier, with baseline quarter
medians of 3.157, 3.063, 3.120, and 3.078 ms and candidate medians of 3.156,
3.078, 3.107, and 3.113 ms. Its prior +5.18% controlled-row observation is
therefore not reclassified as within-run drift; its disposition remains the
byte-identical runtime source and the broader process/source-tree bias.

Full-capture canonical zlib-ng FCOMMENT medians are more stable at -1.75%
(v2), -0.67% (v3 original), and -1.43% (v3 swapped), but they are descriptive
and do not retroactively change the locked minimum statistic.

Nor do the apparent v3 ranges establish a universal noise floor: the high-level
FNAME minimum changes from +3.84% in v2 to -3.07% in v3, a 6.90 percentage-point
same-source swing. The swapped v3 capture also has a -7.67% canonical
first-half FNAME minimum (raw +8.31%), despite its -2.94% full-capture
canonical minimum. This additional same-source threshold crossing reinforces
that a favorable full-capture endpoint cannot adjudicate the row. The targeted
minimum result is therefore inconclusive at a
5% threshold for these high-level header rows. The disposition is instead
source attribution: exact inspection confirms that runtime source is
byte-identical apart from `__version__`, so these movements cannot be caused by
a b1 codec or high-level implementation change. No performance improvement is
claimed. The original, process-level, v2, and v3 captures remain committed.

The two v3 commands were reconstructed from shell history, and their
orientation and normalization formula were derived from the retained source
identities. All three were added to the JSON after capture and are explicitly
non-contemporaneous; timing samples were not changed. Future records store
command, host, orientation, and formula at capture time. The original command
uses exact a4 as `--baseline-root` and the b1 checkout as `--candidate-root`;
the swapped command reverses those roots.

## a4 supplement

| Row | stdlib change | zlib-ng change |
| --- | ---: | ---: |
| bounded JSONL `iter_batches()` | -0.87% | +0.20% |
| full binary read throughput | +1.21% | +1.19% |

The supplement allocation row's timing is informational. Its measured peak
changed only 0.0023% for stdlib and 0.0184% for zlib-ng. Codec peak allocations
were equal to the byte or within 24 bytes of exact a4.

The original a3 capture did show the high-level incomplete-FCOMMENT peak move
from 1,062,097 to 2,108,514 bytes, a 98.52% single-sample swing. Historical a4
records contain both approximately 1.06 MiB and 2.11 MiB modes on identical
code, so one allocation sample cannot classify that movement. The corrective
investigation collected 15 samples per source tree and engine:

| Row and engine | a4 median / max bytes | b1 median / max bytes |
| --- | ---: | ---: |
| FNAME, stdlib | 2,108,890 / 2,119,259 | 2,108,810 / 2,112,377 |
| FCOMMENT, stdlib | 2,108,770 / 2,110,010 | 2,109,026 / 2,110,330 |
| FNAME, zlib-ng | 2,109,090 / 2,112,945 | 2,110,266 / 2,118,443 |
| FCOMMENT, zlib-ng | 2,108,930 / 2,110,170 | 2,108,890 / 2,110,114 |

The low mode appeared on both sides in stdlib and on the exact-a4 zlib-ng
FCOMMENT side; modal medians differ by at most 0.06%, and the worst maximum
increase is 0.26%. The repeated evidence resolves the apparent doubling as
pre-existing measurement bimodality, not a new allocation peak.

Scheduler p95 gaps for the one-item cases were lower. Maximum gaps were also
lower except for zlib-ng 16 MiB (+1.90 us, +0.28%) and 32 MiB (+0.48 us,
+0.07%); both remain within the established scheduler behavior. There is no
memory or scheduler regression after the repeated investigation.

## Disposition

The correctness-bearing benchmark, memory, scheduler, high-level integration,
and retained tiny-write evidence contains no attributable b1 runtime
regression. The zlib-ng FCOMMENT component is non-stationary, and the broader
high-level header minimum diagnostic is inconclusive at a 5% threshold because
of that drift and the cross-capture FNAME swings; it is not counted as proof of
a tighter noise floor. The steadier stdlib FCOMMENT record is not mislabeled as
within-run drift. Exact source comparison shows no runtime implementation
change capable of causing these movements. No performance improvement is
claimed for b1. Hosted CI and exact-head independent review remain separate
release gates.

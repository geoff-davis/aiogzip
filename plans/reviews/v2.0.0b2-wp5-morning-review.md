# WP5 morning collection and review

These post-processing tools do not change the frozen September 28 setup. They
never start benchmarks, alter units, replay captures, send messages or close gates.
They may be run after the service has finished. Use the working checkout's tools,
not the older pinned measurement harness, for post-processing.

## September 28 procedure

1. Inspect `systemctl --user status aiogzip-wp5-onecore-20260928-g08-throughput-stdlib.service`
   and its journal. Confirm the service and descendants have stopped. An inactive
   service alone does not prove success: inspect the runner status and errors.
2. Run the collector with the frozen manifest, completed result directory and a
   fresh archive destination:

   ```sh
   uv run python scripts/collect_b2_timing_window.py \
     --manifest .cache/wp5-qualification-onecore/scheduled/aiogzip-wp5-onecore-20260928-g08-throughput-stdlib.json \
     --run .cache/wp5-qualification-onecore/results/aiogzip-wp5-onecore-20260928-g08-throughput-stdlib \
     --output .cache/wp5-qualification-onecore/review/20260928-g08-stdlib
   ```

3. Read `README.md`, `review.json`, `raw-sha256.json`, raw status/events and the
   raw logs. Preserve rejected captures as well as accepted ones. A collector error
   means no trustworthy derived conclusion; it does not justify deleting the input.
4. Review `throughput.json`: all four block slots, baseline/candidate drift,
   investigation flags and missing evidence. Give Claude the archive path, scope,
   sampling protocol and questions; request read-only review without new benchmarks.
5. Only after review, archive the bundle into the evidence record and disable the
   expired one-off timer. No other window is authorized until its outcome is reviewed.

The collector refuses live/unsettled status, symlinks, changing inputs and output
reuse. It snapshots every regular file in the result tree, preserving bytes and
recording SHA-256. It reconciles the frozen manifest, state, capture hashes, source,
harness, engine and affinity before analysis. All derived comparisons use the
archived copy. Corrupt or inconsistent evidence still gets a raw archive and an
`analysis_errors` record; the CLI exits nonzero and omits continuation advice.
All derived files in such a bundle are untrusted, even if an earlier analysis step
created them. Analysis parses status from the hashed archived copy.
Missing status (for example failure before runner initialization) or a hard kill
leaving `running` requires manual journal/raw-file preservation and investigation;
do not relabel it complete merely to run the collector. No original file is edited.

## Additional reports

For G06, the bundle adds `scaling.json` and a Markdown table. Size pairs must be
exact doublings within the same encoding/newline/content/chunk-size family. Ratios
pair the same capture position and source within each complete block; rejected
blocks contribute none. Input dispositions remain visible, including inconclusive
rows. These finite-size observations are not proof of asymptotic complexity.

For G07 and G08 scheduling, accepted captures produce `observations.json` and a
Markdown summary. The grouping includes source, harness, engine, environment,
affinity and fixture identity. G08 retains every ticker sample, including zero ticks
and the entire final starvation gap. G07 retains complete raw handle outcomes,
separates per-handle output/EOF/error latency, and reports cohort time separately.
It does not reinterpret error latency as successful first-byte latency. Counts,
minimum, median, maximum and raw values are retained; there is no significance or
preemption-bound claim. Original setup warms the core, and pinning limits concurrency.

Standalone use is available through `summarize_b2_observations.py`: G06 consumes
one comparison JSON; G07/G08-scheduling consume capture JSONs. Standalone summaries
are descriptive and do not establish that supplied captures form a complete series.
The collector provides runner-state/hash reconciliation before using them.

## Continuation review

`continuation-review.json` is deliberately non-executable. It includes only slots
marked unstarted with no capture records. Complete and rejected slots are preserved,
never replayed. Original slot IDs and command sides remain intact: a BAAB slot cannot
be renumbered to ABBA just because it is first in a continuation. No plan is emitted
if collection or analysis is invalid.

Before preparing the one permitted continuation, verify unchanged source, harness,
environment, CPU, sampling and host-policy pins; retain parent manifest/status hashes,
all prior data and explicit window boundaries. Repeat declared warmups. Mark the
new manifest with `continuation_of`; a run carrying that marker cannot generate
another continuation recommendation. The current manifest generator handles initial
series only, so implementing/freezing a continuation still requires review. An
aggregate report must merge only the original unstarted slots and keep prior
complete/rejected positions and both windows' provenance. No automatic retry occurs.

An all-deferred initial window reports `series_started: false`, no eligible
continuation slots and `new-initial-window-after-review`. The same applies if only
warmups ran. A failed run explicitly requires investigation before any continuation.
Scheduling a new attempt
still requires review and a new window. An incomplete/contradictory status or lost
manifest does not authorize reconstructing successful evidence from loose captures.

## Architecture statement

The candidate preserves the a3 architecture: immutable compressed-input
spans, the shared incremental gzip-header parser, bounded inflate windows,
cooperative async scheduling, one active owner per codec operation, one
logical task per open high-level handle, same-call sink-error timing,
poisoning/recovery-data sequencing, and replay-based seek recovery.

The only production behavior changes are exact public Boolean validation and
retention of immutable, trailer-validated `GzipMemberInfo` records after a
later decoder failure or explicit discard. No second parser, background
producer, unbounded queue, cross-call write buffer, public integration helper,
new dependency, or new archive format was introduced.

## Public behavior changes

1. Public Boolean configuration is exact. `True` and `False` are accepted;
   integers, strings, containers, enums, NumPy-like scalars, and arbitrary
   truthy/falsy objects raise `TypeError` without invoking truthiness.
2. Public `closefd` accepts exact `True`, exact `False`, or `None`. `None`
   retains its ownership-default meaning.
3. Validation occurs at the public call boundary before resource acquisition,
   engine construction, warning emission, codec reservation, lazy-source
   iteration, or filesystem effects.
4. When member collection is enabled, a decoder retains only immutable records
   for members whose CRC and ISIZE trailers completed before a later failure,
   operation abandonment, or codec-wide discard.
5. The decoder remains unusable after failure/discard, `finished` remains
   false, the failed/incomplete member is never recorded, and transient codec
   state is still released.
6. No high-level lifecycle, exception-timing, recovery-data, write-visibility,
   or same-handle ownership contract intentionally changed.

## Decoder terminal-state matrix

| Completed prefix | Terminal event | Collection | Expected public state |
| ---: | --- | --- | --- |
| 0 | malformed/corrupt/truncated member | on | `member_count == 0`, `members == ()`, unusable |
| 1+ | later CRC/ISIZE/body/header/truncation/limit failure | on | exact validated prefix retained; no failing record; unusable |
| 1+ | active operation closed | on | exact validated prefix retained; no partial record; unusable |
| 1+ | decoder discarded | on | exact validated prefix retained; transient state released; unusable |
| any | repeated discard | on | retained tuple unchanged; discard idempotent |
| any | any failure/discard | off | `members == ()`; `member_count` still counts validated trailers |
| any | complete successful stream | on | all validated members retained; `finished is True` |

Fixed tests cover CRC, ISIZE, malformed/reserved/optional headers, body and
trailer truncation, limits, trailing data, operation close, discard timing,
padding, empty members, member offsets/sizes, FHCRC, filename, comment, extra,
and `mtime=0`. Randomized tests vary zero through six valid prefix members,
failure position/category, optional fields, padding, compressed-input
fragmentation, output chunk sizes, collection mode, and engine.

## Integration behavior and failure evidence

### Fragmented transport

- Uses only top-level public codec classes and `CodecOperation`.
- Uses a bounded, bidirectional in-memory asyncio transport with `maxsize=1`
  queues rather than loopback TCP. Section 9.3 permits an equivalent local
  transport; this choice retains explicit framing, backpressure, EOF, and
  cancellation while avoiding packet-boundary and port/timing flakiness.
- Exhausts or explicitly closes every operation; retained operations are
  invalidated deterministically by codec discard.
- Applies bounded application framing and transport backpressure.
- Labels decoded records provisional until `finish()` validates the trailer.
- Covers whole-stream, one-byte, 1/97-byte, deterministic-random, optional
  header, trailer, and concatenated-member fragmentation.
- Covers zero records, Unicode, records larger than an output chunk, truncated
  CRC/ISIZE trailers, corruption, sender drain cancellation, receiver
  cancellation, finalization error, and early abandonment.
- Verifies output record digest/member count and stdlib `gzip.decompress()`
  interoperability on successful wire streams.

### Concurrent staged ingest

- Uses one public high-level aiogzip handle per shard-owning task.
- Uses `TaskGroup`, a semaphore, bounded `iter_batches()`, per-shard expansion
  limits, and an application-local locked dataset-byte budget.
- Parses JSON incrementally, writes only per-shard staged files, creates the
  manifest after all shards validate, and publishes with one same-filesystem
  directory rename.
- Covers one/three/five shards, more tasks than semaphore permits, empty and
  Unicode data, oversized lines, final-line policy, deterministic delayed
  progress, bad CRC, truncation, invalid JSON, per-shard/global limits,
  simultaneous failures, staged write failures, read/write cancellation, and
  cleanup with Windows-compatible paths including spaces.
- Failure and cancellation tests assert no final destination, no staging leak,
  bounded active handles/batches, and no surviving task.

No integration exposed a recurring operation-ownership problem or required a
private hook. The material application obligation in both cases is to treat
decoded output as provisional until normal gzip completion.

## Known limitations and deferrals

- The codec API remains provisional throughout `a4`.
- Arbitrary gzip random access remains replay-based; indexed access is deferred
  under issue #72.
- AnyIO/Trio high-level adapters remain deferred under issue #71.
- Tiny individual writes retain strict same-call sink/error semantics and are
  slower than bounded batching. The local issue #86 disposition recommends
  closing the 2.0 optimization request or reframing a future explicit buffered
  writer.
- HTTPX guidance is deferred post-2.0. If revisited, it should use
  `Accept-Encoding: identity`, `aiter_raw()`, and staged publication without a
  core runtime dependency.
- The examples are maintained application patterns, not public frameworks or
  turnkey transport/ingest products.
- Staged-ingest atomic no-replace publication uses Linux `renameat2`, macOS
  `renamex_np`, and Windows native rename behavior. Older Linux libc or
  filesystem combinations without `RENAME_NOREPLACE` support fail closed
  rather than falling back to replacement semantics. Missing libc support
  raises `ENOTSUP`; unsupported filesystems preserve their native error, such
  as `EINVAL`.
- The fragmented example's loopback is an equivalent bounded in-memory byte
  transport, not an actual TCP socket integration.
- Provisional payload from a member is not integrity-validated until its
  trailer and stream completion succeed.
- Release-prep version/changelog changes and exact package-head platform CI are
  complete. Tagging, publication, documentation deployment, and issue updates
  are not performed by this packet.

## Questions for independent reviewer judgment

1. Is rejecting all non-exact Boolean substitutes the right pre-beta public
   compatibility boundary, including unused-in-mode options?
2. Is retaining immutable validated-prefix member records after `discard()`
   coherent while the decoder itself remains permanently unusable?
3. Do the examples make operation exhaustion/abandonment and
   provisional-versus-verified output sufficiently difficult to misuse?
4. Is staged directory publication plus per-shard/global limiting a clear,
   bounded high-level integration pattern across supported platforms?
5. Are the controlled optional-header results adequate evidence under the
   written 5% investigation / 10% blocker policy?
6. Did any change unintentionally alter a3 ownership, poisoning, recovery,
   write visibility, or exception timing?
7. With remote platform CI and renewed review complete, is the evidence strong
   enough to choose `2.0.0b1.dev0`, or does a concrete public-contract issue
   require `2.0.0a5.dev0`?

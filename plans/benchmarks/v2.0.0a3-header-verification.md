# v2.0.0a3 Header Verification

## Scope and sources

WP3 verifies that WP2 removed the file reader's duplicate optional-header
buffer without changing the bounded decoder architecture. The locked
comparison harness was SHA-256
`813e99de16c95d0f2805de5f07903d58ca31370f630406e1c7dd7e6c68762a89` for both
the exact `v2.0.0a2` baseline (`9534eb31`) and the stable WP2 candidate
(`50f87f09`). Both source attestations were clean.

Primary raw inputs:

- `v2.0.0a2-a3-baseline-{stdlib,zlib-ng}.json`: exact-a2, 1 MiB source chunks;
- `v2.0.0a3-wp3-headers-{stdlib,zlib-ng}.json`: candidate primary samples;
- `v2.0.0a{2,3}-wp3-headers-64k-{stdlib,zlib-ng}.json`: 64 KiB fragmented
  controls;
- `v2.0.0a{2,3}-wp3-members-rerun9-{stdlib,zlib-ng}.json`: same-session
  many-member controls;
- `v2.0.0a3-wp3-members-10000-{stdlib,zlib-ng}.json`: release diagnostic;
- `v2.0.0a3-wp3-headers-rerun21-pinned-{stdlib,zlib-ng}.json`: final scaling
  samples;
- `v2.0.0a3-wp3-release-headers-{stdlib,zlib-ng}.json`: allocation ownership,
  path, text, and real 128 MiB boundary checks.

All files are under `plans/benchmarks/data/`. Fixture construction, hashes,
and correctness checks were outside ordinary wall-time regions. Tracemalloc
samples are separate and are not used as timing claims.

## Structural and functional result

There is now one header parser: `_GzipHeaderParser`. Neither
`_header_probe_buffer` nor `_try_parse_gzip_header_mtime` exists, and
`_binary.py` no longer parses gzip magic, flags, optional fields, terminators,
or FHCRC.

Deterministic sentinels cover:

- fixed-header splits at bytes 1, 2, 3, 4, 9, and 10;
- XLEN, FEXTRA completion, FNAME/FCOMMENT terminators, and split FHCRC;
- a valid combined FEXTRA+FNAME+FCOMMENT+FHCRC member;
- corrupt FHCRC before public `mtime` commit;
- incomplete optional fields remaining non-errors until source EOF;
- rejection before consuming the first byte over the parser limit;
- public `mtime` remaining `None` for an over-limit header;
- exact linear source-read counts and bounded source returns;
- no compressed rewind cache for a seekable memory source;
- the intentional cache for a non-seekable source;
- text-mode delegation through the same parser.

The real boundary verifier passed under both engines. A header of exactly
134,217,728 bytes reached EOF and failed as truncated; a 134,217,729-byte
header failed with the 128 MiB safety-limit error. Both retained `mtime=None`,
and sources never returned more than the requested 1 MiB.

## Allocation ownership

The 32 MiB primary allocation gate improved by 33–66x versus exact a2:

| Engine | Field | exact a2 peak | candidate peak | reduction |
| --- | --- | ---: | ---: | ---: |
| stdlib | FNAME | 69,994,281 B | 1,059,505 B | 66.1x |
| stdlib | FCOMMENT | 69,994,281 B | 2,108,388 B | 33.2x |
| zlib-ng | FNAME | 69,994,761 B | 1,059,025 B | 66.1x |
| zlib-ng | FCOMMENT | 69,994,865 B | 1,059,025 B | 66.1x |

Every candidate peak is below the 4 MiB target and the 8 MiB hard gate.

The separate 64 MiB retention checks peaked at 1.06–1.14 MiB. After close and
garbage collection, current traced allocation was at most 81,824 bytes; no
header-sized object remained. The first sample includes persistent executor
startup allocation, explaining its higher post-GC current value.

The non-seekable 32 MiB control intentionally retained exactly 33,554,442
compressed bytes in its rewind cache and peaked at 36,450,459 bytes. That
allocation belongs to the documented rewind feature, disappears after object
disposal and GC, and is excluded from parser-memory gates.

At 64 KiB source fragmentation, the candidate used 68,201 peak Python bytes
for each 16 MiB incomplete case versus 35,275,657 bytes on exact a2, a 517x
reduction.

## Scaling and throughput

The machine exposed 32 CPUs with the `powersave` governor and boost enabled.
At 1–9 ms absolute durations, unpinned runs showed scheduler-migration noise
and some apparent ratios above 2.5x. Those raw nine-sample runs are retained.
The plan-required investigation pinned the benchmark to CPU 0; a final 21
samples resolved the ratios:

| Engine | Field/form | 16→32 MiB | 32→64 MiB |
| --- | --- | ---: | ---: |
| stdlib | FNAME complete | 1.85x | 1.98x |
| stdlib | FNAME incomplete | 2.38x | 1.94x |
| stdlib | FCOMMENT complete | 2.18x | 1.97x |
| stdlib | FCOMMENT incomplete | 2.32x | 1.95x |
| zlib-ng | FNAME complete | 2.16x | 1.99x |
| zlib-ng | FNAME incomplete | 2.21x | 1.89x |
| zlib-ng | FCOMMENT complete | 2.10x | 2.15x |
| zlib-ng | FCOMMENT incomplete | 2.23x | 2.17x |

All ratios pass the 2.5x hard gate. No parser optimization was needed.

Against exact a2, primary 64 MiB high-level cases were 48–70x faster with
1 MiB source chunks. With 64 KiB fragmentation, 16 MiB high-level cases were
38–52x faster. The repaired high-level path is now within approximately
0.5–2.2 ms of the direct decoder at 16–64 MiB; that remainder is the expected
async source reads, list assembly, and file-wrapper lifecycle cost rather than
duplicate parsing.

The primary 1,001-member stdlib sample was initially 8.6% slower than the
earlier exact-a2 run, which triggered the required nine-sample same-session
investigation. The controlled rerun was 1.34% faster under stdlib and 0.49%
faster under zlib-ng. Header notification therefore stays within both the 5%
target and 10% hard gate.

The release-only 10,000-member diagnostic completed in 102.17 ms under stdlib
and 97.27 ms under zlib-ng, producing the expected 130,000 bytes and final
alternating timestamp `0xffffffff`.

Direct-decoder outputs, byte counts, and failures remained correct. The final
pinned results keep 64 MiB direct controls effectively flat; the largest
cross-run delta was a 0.18 ms zlib-ng FCOMMENT sample, while the same parser
under stdlib was faster. This is sub-millisecond engine/run noise, not a
decoder architecture change.

The path-backed 16 MiB incomplete FNAME median was 2.35 ms under stdlib and
2.21 ms under zlib-ng. The combined-field text smoke returned the expected
payload and `mtime=123456789` under both engines.

## Disposition

Every hard structural, functional, allocation, scaling, and many-member gate
passes. The removed compatibility parser—not `_GzipHeaderParser` or another
high-level owner—was the time and memory hole. No waiver and no additional
production optimization are required for WP3.

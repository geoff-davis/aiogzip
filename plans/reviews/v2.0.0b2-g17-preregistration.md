### Pinned inputs

Nothing in a run is supplied at launch except `MODE`.

- **Units.** Each run is a systemd user unit started manually. The unit's
  `ExecStartPre` lines check the sha256 of its driver (`run.sh` or
  `preflight.sh`) and of `harness.sha256`.
- **Driver checks.** The driver refuses to start unless
  `sha256sum --check --strict harness.sha256` passes. That list pins
  `quiet_gate.py`, `summarize.py`, `envcheck.py`, both structural step lists
  and every manifest.
- **Manifests.** `manifest-<mode>.json` is the only source of commits,
  roles, the runner commit, the categories, the runner's `benchmarks/` and
  `scripts/` tree hashes, the `uv.lock` sha256 and the installed-environment
  fingerprint. There are no environment overrides.

### Environment comparability

Every run checks the shared venv twice:

- `uv sync --locked --all-extras --check` must find it in sync with the
  pinned lock;
- `envcheck.py` must reproduce the pinned fingerprint, a sha256 over the
  interpreter version, build and resolved paths and every installed
  distribution's version.

The A/A window and the final windows therefore run against one proven
environment. The venv also carries a stale `aiogzip 1.9.1` dist-info beside
the editable install. It is part of the fingerprint, and `--source-root`
imports are verified per capture, so it cannot be measured instead.

The fixtures fall into three groups:

- The write fixtures are deterministic, and their identities (sha256 per
  size) are frozen by the preflight and checked in every capture.
- Every runner and structural payload comes from a seeded or fixed
  generator in the pinned trees, so both sides of every window measure the
  same bytes (plan §15.1). `DataGenerator.generate_binary()`, which the
  `io`, `concurrency`, `memory`, `compression` and `inspection` benchmarks
  use, drew from `os.urandom` until `9ae439b`; it now draws from
  `random.Random(0)`, equally incompressible. Gzip fixtures that a capture
  compresses at run time may differ only in their header `mtime`.
- Where structural rows carry fixture digests, the frozen row signatures
  include them.

### Execution

- **Worktrees.** The driver creates fresh detached worktrees for A, B and
  the runner. A and B are separate even when they share a commit. It
  verifies each commit and a clean tree, the runner's tree hashes, and both
  `uv.lock` copies.
- **Interpreter.** Every step runs the venv's interpreter directly, with
  stdin closed, so nothing re-syncs the venv mid-window.
- **CPU and quiet gate.** Every step is pinned to CPU 13. The WP9 quiet gate
  must see 120 s at 2.5 foreign cores or fewer, and a monitor samples
  foreign CPU every 5 s throughout.
- **Captures.** For each engine (stdlib, then zlib-ng), eight captures run
  in ABBA ABBA order. Each capture runs two steps:
  1. `run_benchmarks.py --category io,micro,concurrency,memory,regressions,read_health,text_origin --repeat 5 --regression-profile quick --regression-mode throughput`
  2. `bench_a3_regressions.py --categories writes --repeat 5` with the
     default sizes (10 B to 256 KiB) and all four write methods.
- **Structural steps.** In the C0 and WP0 windows, these run after the ABBA
  loop, once per side and engine: A then B on stdlib, B then A on zlib-ng.

## Statistics and decision rule

`summarize.py window` refuses any window in which:

- a capture or structural output is missing, incomplete, failed or
  mislabeled;
- a commit, the runner (harness) commit, the requested or active engine or
  the clean state is wrong; structural outputs are checked from their own
  provenance fields;
- a runner capture's row set, including duplicate rows, differs from the
  set the preflight froze for that role and engine;
- a write capture's fixtures differ from the frozen ones, or a write result
  is not `ok` with five samples;
- a structural output's row signature differs from the frozen one. The
  signature is each row's shape at every depth: keys, strings, Booleans,
  nulls and list structure, including lengths. Numbers under a registered
  identity key of that script are kept verbatim: case parameters such as
  line counts, hints, chunk sizes, handle counts and limits, and fixture
  sizes. Every other number is a measurement and is replaced by its type
  name, and each non-empty list made only of numbers by its element types,
  because timed-budget batches (`operation_seconds`) vary in length. The
  identity keys are listed per script in `summarize.py` (`IDENTITY`), and a
  script without an entry is refused;
- a runner duration or write median is not a finite positive number, or a
  `memory` row lacks a `memory_increase_mb` that parses as a finite number
  (`bench_memory` records it formatted, such as `"12.3"`);
- foreign-CPU samples fail to cover any capture or structural step
  continuously;
- foreign CPU exceeds 2.5 cores during any capture or step.

A refused window is rerun whole. The candidate is never rerun alone.

The primary statistic is each benchmark's minimum of the four capture medians
on each side, as in CLAUDE.md method A. The four adjacent A/B pair deltas are
reported alongside it.

Plan §15.1 policy applies to every runner row and write row of the C0 and WP0
windows:

| Slowdown (B against A, by minimum) | Required action |
| --- | --- |
| 5% or less | None |
| More than 5% | Investigation and a recorded disposition |
| More than 10% and attributable to the candidate | Blocks by default |

Adjacent pair deltas inform stability but do not decide eligibility.

**A/A use.** The A/A window reports each row's delta and the largest absolute
delta per engine. A final-window row above 5% is still investigated even if
its A/A row was also above 5%. The A/A result is evidence within that
investigation, not a waiver.

The `memory` category records an RSS increase per capture. It is reported
per capture and judged with the G07 resource rows, not by percentage.

## Structural steps and their criteria

Each step is judged against the criterion recorded when its gate closed, and
the record cites that criterion per row. None of these scripts emits a
pass/fail field. Each raises on a correctness failure, and its numbers are
judged as below.

Where a gate closed with non-default options, the step uses those options so
that the criterion applies unchanged.

## Preflight (needs authorization; not evidence)

`preflight.sh` runs as `aiogzip-g17-preflight.service` (`RuntimeMaxSec=3h`).
It has the same pinned inputs and environment checks as a window. It covers
three roots on both engines: `c0`, `wp0` and `candidate`. The candidate
root is `57098fd`, not the runner `9ae439b`; the two commits' `src/` trees
are identical (`94eb3c9`, as in `a7c3880`), and the runner differs only in
its seeded fixtures. Per root and engine it runs:

- the runner categories once (`--repeat 1`);
- the write sizes with five samples (`--repeat 5`), the minimum that
  `bench_a3_regressions.py` accepts (an odd repeat of at least 5);
- every `structural-c0.txt` step once, with its registered options.

It runs unpinned and with no quiet gate, and its output goes to
`.cache/wp10-bench/preflight-<time>/`. It is never cited as timing evidence.

Its results serve three purposes:

- **Durations** per step set each window's `RuntimeMaxSec`.
- **Compatibility:** any step that fails on a root, notably `read_health`
  and `text_origin` on `dc8950c`, which postdate it but use only the public
  API.
- **Frozen row sets.** `summarize.py preflight` validates every output's
  provenance and writes `expected-rows.json`, the per-role and per-engine
  runner row set, write fixtures and structural row signatures. It notes any
  role whose rows differ from C0's.

An amendment follows the preflight and is reviewed before the A/A window. It
records:

- the durations;
- any incompatibility, with a `manifest-wp0.json` category change if
  needed;
- the hash of `expected-rows.json`;
- the regenerated `harness.sha256`;
- `aiogzip-g17-aa.service`, with its pinned hashes and runtime limit.

### Amendment 3: investigations

The C0 and WP0 windows ran and are recorded in the
[G17 record](v2.0.0b2-wp10-qualification.md#final-windows), which lists every
row above 5% and every structural item outside its criterion. Before any
disposition, two investigations attribute and recheck them. Neither is a
window, and neither replaces one: dispositions cite both investigations
together with the final windows. Both run under `investigate.sh`, pinned to
CPU 13 behind the same quiet gate, foreign-CPU monitor and pinned-input
checks as `run.sh`, with the runner and harness at `f202b46`.

**I1: commit ladder (`PART=ladder`).** `manifest-ladder.json` lists 27
commits: WP0 `dc8950c` (index 00), then one commit for each of the 26 `src/`
changes up to the candidate, in history order. C0 `b074bdc` (index 15)
stands for `2f78925` and `f202b46` (index 26) for `a7c3880`; each pair has
the same `src/` tree. Every index has a distinct `src/` tree. For each engine,
four rounds run every commit in forward, reverse, reverse and forward order.
Each step runs the runner with `--category io,micro,read_health --repeat 5`,
which covers every flagged runner row except the write sizes, none of which
was above 5%.

- A step that fails is recorded in `failures.tsv`, and the run continues.
  The failed commit is excluded from all four rounds on that engine, so its
  boundary spans the nearest surviving neighbours. A failure at either
  endpoint (index 00 or 26) refuses the run.
- `summarize.py ladder` validates every capture with the window checks:
  status, categories, repeat, profile, target commit and clean state,
  runner commit, requested and active engine, finite positive durations,
  continuous foreign-CPU coverage, and no capture above 2.5 foreign cores.
  A commit's row set must be the same in all four rounds. A row present at
  only some commits is reported across the commits that have it: its
  boundaries join each such commit to the next one that has it, and its
  endpoint ratio is reported only when both endpoints have it.
- **Primary statistic.** For each row and each boundary between adjacent
  commits, the four within-round ratios (later commit over earlier, from the
  same round) are reported as percentages. **Secondary:** the ratio of each
  commit's minimum over the four rounds, and the same endpoint ratio from
  index 00 to index 26.
- **Stable jump.** A boundary is a stable jump when all four within-round
  ratios exceed +2%, or all four fall below −2%. The flagged rows (flush,
  `read1`/`readinto1` at 4 KiB, 17-byte `readline`, `read(-1)` at 1 MB, and
  the three `read_health` rows) are reported first.
- **Confirmation.** A stable slowdown jump that would carry a row's
  disposition is then confirmed by an adjacent-pair ABBA window on that
  boundary, registered in its own amendment before it runs. The ladder
  alone attributes; it does not decide.

**I2: order check (`PART=order`).** `manifest-order.json` pins A to C0
`b074bdc` and B to the candidate `f202b46`. `structural-order.txt` lists
each step that was outside its criterion, with its registered options. Each
step runs four times per engine in positions A B B A:

| Step | Engines | Options |
| --- | --- | --- |
| `g03-source-reads` | zlib-ng | default |
| `g05-pending-bulk-4m-repetitive` | zlib-ng | `--category bulk --repeat 15 --chunk-size 4194304 --payload repetitive` |
| `g06-longline-timing` | zlib-ng | the registered G06 timing options |
| `g07-read-latency-r7` | stdlib, zlib-ng | `--phase latency --repeat 7` |

- `summarize.py order` validates provenance, engine, foreign CPU and
  coverage as in a window. The first three steps' row signatures must equal
  the frozen C0 and candidate signatures. Each `g07-read-latency-r7` output
  must hold exactly seven rounds (0–6) of the frozen set.
- **Timing steps.** For each row, it reports two statistics. The row
  minimum (`minimum_seconds` for `g03`, `minimum` for `g05`, `min_seconds`
  for `g06`) is the statistic the final-window flags used, and it reconciles
  them. The row median shows stability. For each statistic it gives the two
  opposite-order pair deltas (2B against 1A with C0 first, 3B against 4A
  with the candidate first) and the delta of the per-side minimums. For each
  position it also gives the minimum, the median, the sample count and the
  sample range: `seconds` for `g03` and `g05`, and each timed batch's
  per-operation `seconds` for `g06`. Every sample stays in the archived
  outputs.
- **`g07` latency.** It refuses any group with zero ticks, and any group
  whose handle outcomes vary across rounds or between C0 and the candidate.
  For each group, it reports the cohort max/min over the seven rounds in
  each file (the WP5 criterion is at most 1.5), the pooled max/min per side,
  and the candidate-to-C0 ratio of the minimums.

**Dispositions.** Every row above 5% in a final window receives a recorded
disposition. Each disposition cites:

- the balanced rerun (I2, or the I1 rounds for runner rows);
- the source boundary the ladder attributes, or a statement that it
  attributes none;
- a code-path explanation;
- reconciliation with the final windows' endpoint deltas;
- an explicit decision.

Under §15.1, a confirmed G03 slowdown above 10% that is attributable to the

**Method.** `confirm.sh` runs as `aiogzip-g17-confirm.service`. It has the

**Statistic and rule.** `summarize.py confirm` validates every capture as
the ladder does, and requires one row set across a pair's captures. For
each row, it reports the method-A delta (minimum of the four capture
medians per side) and the four adjacent pair deltas. A jump is
**confirmed** when the delta is beyond ±2% and all four pair deltas share
its sign strictly: all above zero for a slowdown, all below zero for a
speedup. A zero pair delta confirms neither. It reports the rows above 5% in a final window first, then every
other row beyond ±5%.

A disposition may cite a ladder attribution only if the corresponding pair
confirms it in the same direction. If a pair does not confirm, the
disposition says so and rests on the final windows alone.

# WP5 bounded timing windows

This increment provides `run_b2_timing_blocks.py` and
`prepare_b2_timing_window.py`. It preserves the frozen September 27 runner and
manifests, changes no production code and schedules nothing. The original quiet
policy remains enforced: at most 0.25 foreign cores, load1/load5 at most 0.5,
and 120 quiet seconds before starting. Busy windows can therefore still defer.

## Manifest preparation

The generator accepts a gate (`G06`, `G08-throughput`, `G08-scheduling`, `G07`),
engine, clean baseline/candidate/harness checkouts, copied Python executable,
output directory, service name and manifest destination. Its own checkout supplies
the runner pin. Use dedicated clean worktrees for runner and harness; edits or
untracked files in a frozen checkout abort execution. Paths, full commits, interpreter
and lockfile hashes are recorded. These hashes do not attest every installed file
in the copied environment; do not modify that environment between windows, and
review dependency records across windows as well as within each comparison.
Optional `--not-before` and `--deadline` must be supplied together; omission yields
a deliberately non-runnable draft. Preparation launches and schedules nothing.

G06 and G08 throughput manifests retain both discarded source warmup captures and
four ABBA/BAAB blocks, with nine batches/discard two/seven retained samples. G06
retains all 175 cases; G08 retains all 16 cases per engine. The generator emits the
corresponding comparison settings. G08 scheduling uses seven original ticker
samples per capture without batching. G07 uses seven rounds of both engines in
alternating order, one full 104-case fresh-process matrix per engine per round.
G07 ignores the single-engine selection because its manifest always includes both.

Prepare separate G06 engine windows and separate G08 throughput/scheduling engine
windows; G07 has one combined-engine manifest. The default initial reserve is three
hours of remaining window for G06, and thirty minutes for other scopes. These are
execution bounds, not measured completion-time promises. Each command has a
30-minute timeout. Each block requires and enforces a one-hour reserve/span for
G06, or thirty minutes for other scopes. If too little time remains, leave that
block unstarted; exceeding the span rejects it before it could be misreported as
complete. The comparison index uses that same span. The entire window is bounded to at most four hours. A frozen
manifest needs an explicit future timezone-aware window and a fresh output path.

## Execution and outcomes

Run `python scripts/run_b2_timing_blocks.py MANIFEST --check` to validate without
launching. Actual execution must be inside the dedicated service named by the
manifest (`aiogzip-wp5-*.service`). Register that service with
`KillMode=control-group`, a runtime cap matching its window plus cleanup grace,
and a stop timeout allowing child termination. No unit is installed by these tools.

Before launching, and before/after each successful capture, check frozen source,
harness, runner and file identities. All commands use argv lists, explicitly pinned
to the manifest CPU (13 by default); no shell command interpolation is used.
Each output/log name is unique and existing captures cannot be overwritten.

CPU accounting subtracts the entire dedicated cgroup, including exited children.
The runner records per-core/sibling counters, instantaneous frequency and k10temp
when available, explicitly labelling unavailable optional sensors. Required global
CPU/cgroup accounting failures abort. Load limits apply during quiet preflight;
during measurement, foreign CPU is the interference criterion, because benchmark
work itself raises load. Host samples and command boundaries are retained in JSONL.

Warmups must finish before retained blocks. Each block is attempted once. A rejected
block retains its partial captures/logs, and earlier complete blocks remain complete.
After interference, re-establish the quiet period before the next block; never replay
the rejected block. A deadline stops active work and leaves later slots unstarted.
A command failure or timeout stops the window for investigation. Exceptions/signals
record the active block's rejection and preserve earlier state. Status writes are
atomic. A running slot is published as rejected in the comparison index, with an
interrupted-runner reason, so an unhandled hard crash cannot make started work look
unstarted. Completed blocks have no rejection reason. Interrupted command records
are retained in status as well as events. The service must remain responsible for all descendants during shutdown.

The runner publishes a comparison index for throughput manifests, directly from
block status and declared command sides, with capture paths relative to that index.
Running/unstarted blocks cannot contribute accepted timing rows. The separate
comparison tool checks declared sampling and chronology; neither tool closes gates.
G07 and scheduling outcomes remain descriptive evidence for review.

## Continuation and policy boundaries

This runner executes a fresh window only. It never schedules retries or automatically
combines windows. If a series is incomplete, the reviewed protocol allows one
separately scheduled continuation of unstarted slots. Preparing that continuation
requires preserving the original status and selecting only those slots, checking
unchanged pins/protocol and retaining window boundaries; a continuation manifest
and aggregate report need review before execution. Completed/rejected slots are not
replayed. The generator currently prepares initial full series only.

Concrete timestamps, any change to the quiet threshold, service registration and
actual evidence collection remain pending. No policy change can be hidden in a
manifest: the runner rejects any quiet-policy object differing from its fixed policy.

Monitoring uses intervals of at most five seconds. A child exiting just before a
timeout may be conservatively rejected when that sample ends at the boundary;
this cannot create a false accepted capture. After interference, the runner’s own
load may take several minutes to decay before a new quiet period can complete.

## Review and validation

Claude reviewed the runner/generator through Herdr, including a fake-clock probe.
Its requested per-block reserve/span enforcement and crash-time index correction
are included, with regression tests. Its final review found no blockers; all 20
runner tests pass. The local full suite passed 3,516 tests with one skip, and
all-file prek passed. No benchmark command was launched during validation.

The default block durations remain planning bounds, not new timing evidence.
Earlier G07 resource-log spans (about 27 seconds stdlib and 22 seconds zlib-ng)
provide rough headroom context, but resource runs do not predict latency-mode
runtime. Review these bounds with actual command wall durations before freezing a
later schedule; retain span-rejected blocks and never enlarge limits retrospectively.
The conservative G06 reserve can leave a late block unstarted even if it might have
finished; that is preferable to consuming a non-replayable slot at the deadline.

## Subsequent policy decision

The initial f756810 runner and draft manifests used the strict 0.25-core ceiling
as recorded above. The [subsequent provisional policy](v2.0.0b2-wp5-provisional-quiet-policy.md)
changes only the new runner's foreign-CPU ceiling to one core. Its load and quiet-period
requirements remain unchanged; new manifests must name the new runner commit.

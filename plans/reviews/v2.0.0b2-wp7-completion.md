## Exit criteria (§11)

- **One coherent origin.** The five old names are not slots and no production
  code reads, stores or deletes them (AST test). The live origin is one object
  for the life of the handle and is updated in place.
- **No aliasing.** The rollback state holds an immutable five-field tuple,
  unchanged when the live origin is mutated; `restore()` copies it into the
  live object. A pending origin is never the live object and does not move
  when the live origin is mutated while it is published. The only shared value
  is the decoder state, an immutable `(bytes, int)` under the `codecs`
  `getstate()` contract, checked for five codecs.
- **Pending-origin lifecycle.** For each producer (sized read, fast line,
  buffered readline), the origin is published once, keeps its identity and
  value across the read, and is cleared after success, error and cancellation;
  the reader then recovers the whole line.
- **Rollback order matches C0.** A spy on `restore()` shows `readlines()`
  rebuilds the buffer and offset before restoring the origin and clears the
  line batch afterwards, and buffered readline appends recovered text only
  after the restore.
- **Cookies and newlines.** The BC6 cookie suite covers replay through every
  producer; a direct test round-trips `tell()`/`seek()` across buffer
  compaction. `tests/test_text_origin.py` (32 tests) and
  `tests/test_text_origin_transitions.py` (18 tests) are new.
- **Supported UTF-16 variants (§11.2).** `utf-16` was already covered by the
  BC6, fragment and small-hint suites. For `utf-16-le` and `utf-16-be`, which
  have no BOM: line reads with a `tell()`/`seek()` round trip at every line,
  compared with `io.TextIOWrapper`, under `newline=None`, `''` and `'\r\n'`
  with 3-, 5- and 7-byte chunks that split code units and surrogate pairs;
  sized-read cookies; a CR exactly at a decode boundary; and both rollback
  paths. The decoder-state immutability check includes both.
- **Rollback from a mid-stream decoder state.** Both rollback tests, for UTF-8
  and both explicit-endian variants, now start from an origin holding a split
  code unit and replay a cookie taken after the rollback. In
  implementer-reported mutation checks (outputs not archived), recording an
  empty decoder state at capture failed all nine; skipping it in `restore()`
  failed six, at least one per encoding.
- **Stale and foreign cookies.** Three existing tests reject a cookie from a
  closed issuing handle at a second handle: two on the same file
  (`test_edge_cases_and_errors.py`, `test_regressions.py`) and one on a
  different file (`test_text_coverage.py`). An arbitrary cookie is rejected. Cookies intentionally stay valid for the whole
  life of the handle that issued them; that is unchanged.
- **C0 traces pass.** File-state, source-failure, opening, opening-cleanup and
  long-line cookie suites: 257 passed on each engine at the branch head.
- **Full suite passes.** Both engine suites: 3,749 passed, 1 skipped.
  All-file prek passes.
- **Hot-path budgets** (below).

## Allocation

`scripts/measure_text_origin_allocations.py` counts `_TextBufferOrigin`
constructions only, by requesting method, over 20,000 lines with 4 KiB chunks
(48 to 52 refills):

| Scenario | Live | Pending | Origin objects per line |
| --- | ---: | ---: | ---: |
| Iterate, `newline='\n'` (fast) | 1 | 9 | 0 |
| Iterate, `newline=''` | 1 | 48 | 0 |
| Iterate, `newline='\r\n'` | 1 | 52 | 0 |
| `readlines(64)` loop, fast | 1 | 9 | 0 |
| `readlines(64)` loop, generic | 1 | 48 | 0 |
| `read(1000)` loop | 1 | 2 | 0 |

Rollback constructs no origin object. It does allocate per capture: a
five-field tuple nested in the rollback-state tuple, where C0 built one flat
seven-tuple. The probe does not count those tuples. At C0 the pending origin
was a five-tuple built at the same sites, so the per-refill count is unchanged.

## Benchmarks

Method A, as for G10: `io,micro,text_origin` against clean C0 and candidate
worktrees, the same frozen venv, both engines, eight captures per engine in
ABBA ABBA order with five repeats each, pinned to CPU 13, compared by
per-benchmark minimum of capture medians. Codex reviewed the scripts and units
before each run.

### First window: regression found

The window was registered for 02:15 on October 6. At the maintainer's request
it ran early, at 20:50 on October 5, as a manual start of the same unchanged
unit; the timer was then disabled. The quiet gate passed and peak foreign CPU
was 0.33 cores.

Every row was within ±2.2% except `readlines(64) loop - 20K lines`: +9.64%
(stdlib) and +10.07% (zlib-ng), every pair between +9.2% and +11.4%. Each
`readlines()` call took a rollback `snapshot()`, a method call plus a
Python-level dataclass construction. In isolation that capture cost 77 ns
against C0's 51 ns; an inline field tuple costs 41 ns. `4ebd209` adopted the
tuple. An exploratory interleaved `readlines(64)` micro-test (stdlib) measured
C0 3.692 ms, `cb90a75` 4.005 ms (+8.5%) and the fix 3.764 ms (+1.9%).

### Rerun: candidate `feea4a4`

A new unit differing only in its description and candidate SHA was reviewed,
installed without a timer and started manually at 21:04 on October 5. The
quiet gate passed and peak foreign CPU was 0.38 cores. `feea4a4` has the same
source, benchmarks and `uv.lock` as `4ebd209`.

- **`readlines(64)` loop:** +1.13% (stdlib, pairs +1.1 to +2.3) and +2.12%
  (zlib-ng, pairs +0.7 to +2.4). Fixed, within policy.
- **`text_origin`, others:** within ±0.5% on both engines.
- **zlib-ng:** one flag, `Text large reads` at +36.73%, from a single pair
  (+37.0, +2.3, −0.1, −0.1). That benchmark is bimodal within a capture
  (samples near 0.31 ms or 0.43 ms), and the first C0 capture's median fell
  in the fast mode. Candidate samples reach the same fast mode (0.314 ms), and
  the targeted micro-test below shows no zlib-ng difference. The next largest
  row is `Text read (bulk)` at +4.70%, below the 5% threshold.
- **stdlib:** one flag, `Text large reads` at +6.44% (pairs +2.0, +0.4, +5.5,
  +6.4); every other row within ±2.1%.

### Follow-up: `Text large reads` on stdlib

The benchmark times one 1 MiB `read(n)` with 64 KiB chunks, about 16 refills;
WP7 adds a few attribute stores per refill, far below the measured gap. A
targeted micro-test in fresh processes, interleaved, timed that read 60 times
per process:

| Probe (stdlib, steady-state medians) | C0 | WP6 (`0b3fab0`) | `cb90a75` | `feea4a4` |
| --- | ---: | ---: | ---: | ---: |
| Default allocator | 1.890 ms | 2.073 ms | 2.098 ms | 2.040 ms |
| `MALLOC_MMAP_THRESHOLD_=131072` | 2.214 ms | 2.213 ms | — | 2.423 ms |
| `MALLOC_MMAP_THRESHOLD_=67108864` | 2.152 ms | 2.126 ms | — | 2.010 ms |

On zlib-ng the same probe gave C0 and `feea4a4` the same medians (about
0.31 ms). With the default allocator the stdlib gap is already present at WP6,
before any WP7 change, and the G10 window flagged the same benchmark at +5.66%.
G10's micro-test, which timed the read per operation after a warmup, did not
reproduce that flag; this fresh-process probe does, so the probe's own
allocation history matters.
Fixing glibc's mmap threshold, which disables its dynamic adjustment, moves
`feea4a4` from +9.4% to −6.6% against C0, and WP6 from 0% to −1.2%. The gap
present before WP7, the zlib-ng control, the benchmark's bimodality and this
sign reversal are inconsistent with a stable intrinsic WP7 cost. The
underlying cause was not measured directly: an allocation-shape difference
can interact with allocator policy, as with the G06 ISO-2022-JP rows. No
stable WP7 regression is established.

**Proposed disposition:** the `readlines(64)` regression is fixed and within
policy on both engines; the `Text large reads` flags establish no stable WP7
regression and track allocator state. G17 re-measures every family against
both baselines before release.

Evidence, including both windows' raw captures, monitor logs, scripts, units,
summaries, allocation probe and micro-tests, is archived in
[`data/b2/wp7-g11`](../benchmarks/data/b2/wp7-g11/README.md).

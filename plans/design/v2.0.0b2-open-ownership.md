# WP3 opening ownership

BC3 selects rejection of overlapping `open()` and `close()` while acquisition or
initialization is active, using the existing `ConcurrentOperationError`. The
reservation is synchronous and lasts through failed-open cleanup. Normal
already-open/closed errors and repeated close behavior remain unchanged.

The opener owns the resource locally until codec construction, the complete initial
header write or seekability probe succeeds. Publication has no suspension point.
Text opening similarly retains its binary wrapper locally until binary opening
succeeds, then installs observers and publishes it. No partially initialized
resource is visible through the ordinary handle fields.

For standard aiofiles path acquisition, a private executor future owns native open.
WP1 settlement retains it through cancellation and runner shutdown. If cancellation
wins after native acquisition, retrieve and close the result before propagating the
original cancellation. Wrapping failure has the same resource cleanup requirement.
Native initialization writes, probes and failed-open close also settle before
resource release. No helper task or new executor is needed.

Custom asynchronous replacements must finish resource access before returning or
raising, as in WP2. Failed acquisition cannot recover a resource that a custom
replacement hides internally. External file objects remain caller-owned until a
successful open; existing failed-open retry behavior does not close them. After
publication, ordinary `closefd` behavior applies. Ordinary cleanup errors add
diagnostic notes without replacing the original acquisition/initialization
exception or its existing cause.

Exceptional context exit during opening preserves its body exception and does not
claim closure: the concurrent opener still owns the resource and must be awaited
and closed by its caller. Clean exit rejects the conflicting operation, matching
explicit close. Binary and text use the same policy.

Native open and failed-open close use the existing default executor. Native
initialization on supplied aiofiles delegates respects their configured loop and
executor. Each executor future remains private and settled before cleanup;
a queued acquisition may still run after cancellation, then is closed. No cancellation
count is consumed here: these are outside requests, not library-issued aborts.

Cooperative custom cleanup must finish its resource activity before raising, including
on cancellation. No guarantee is made for a replacement that hides a resource or
continues background activity after that boundary. A close failure remains visible
as a diagnostic note; the library does not retry an arbitrary
failed close and risk closing a resource twice.

## Cleanup control-flow precedence

If ordinary acquisition or initialization fails, a cancellation or interrupt during
cleanup takes precedence once cleanup has settled. It must not become a note on
an ordinary exception that a caller can accidentally catch and continue past.
The original failure remains context (attached explicitly if repeated native
cancellation has cleared the implicit context). Existing cause/context chains are
not overwritten. Ordinary cleanup exceptions still become notes; if acquisition
was already cancelled, its original cancellation remains primary through further
cleanup cancellation. No outside cancellation count is consumed.

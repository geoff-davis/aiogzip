# WP5 per-gate timing protocol: proposed implementation

This design follows the September 27 placement diagnostic and maintainer direction
to continue with interleaved comparisons. It replaces further absolute-stability
calibrations with relative measurements. It is not a qualification result, a runnable
manifest, or a modification of the frozen overnight queue. G06–G09 and G17 remain
open. No new execution window has been scheduled.

## Common controls

Use the existing copied Python 3.14.2 environment and clean, pinned source/harness
checkouts. Record full commits, file hashes, package imports, selected engines,
fixture hashes, affinity and environment. CPU 13, sibling 29, is the prospective
fixed placement for both sides: its quieter sibling is a practical choice, not a
claim that it is intrinsically faster or proved superior; its 64-byte diagnostic
case was about 2.5% slower. Never compare absolute
times from different CPU placements or different sampling protocols.

Collect four blocks per engine, alternating ABBA and BAAB, where A is baseline and
B candidate. Every block contains two captures of each version. Engines run
sequentially; engine and time of day are therefore confounded, and no comparison
crosses engines. Retain all results, including warmups and rejected attempts. Before
retained throughput blocks, run one discarded capture per source and engine.
Declare all case matrices and order in the frozen manifest before measurement.

Quiet-machine qualification remains required. The existing runner's 0.25-core,
0.5 load1/load5 and 120-second start policy remains unchanged. A proposed next
runner could use the previously discussed one-core foreign-CPU ceiling, retaining
120 seconds and recording per-core/sibling activity, but that ceiling is not
validated by the diagnostics. Do not silently apply it or remove the load limits.
The concrete runner policy and next execution window must be settled before a
qualification manifest is frozen. No system power settings or unrelated processes
are changed. Use cgroup accounting for the benchmark and exited children, not the
scratch diagnostic's approximate process subtraction.

Monitor and retain host CPU, sibling activity, frequency snapshots and temperature
through each capture. Distinguish unavailable telemetry, deadline expiry and host
interference. Reject an interrupted or contaminated block in full, preserving it;
never remove individual slow samples after seeing timings. The new runner must
retain earlier completed blocks, reject only the affected block, re-establish the
quiet start condition and continue to the next declared block. A contaminated block
is not repeated within the window; it counts as unusable toward the three-of-four
rule. Report its raw data but exclude it from accepted timing summaries, explicitly
labelling any summary with fewer than four uncontaminated blocks. Bound attempts and total
runtime in the new manifest. Implement service identity and deadlines explicitly:
the old runner hard-codes the September 27 service and expired deadline.

## G08: fairness throughput and scheduling

Compare aceca4b (WP4) with f73ae8d (reviewed fairness change), on both engines.
Use a common committed harness incorporating 5b55e17's batching support.
Retain all 32 throughput cases: repeated-text and random-data fixtures, compression
and decompression, four item sizes, both engines, 4 MiB payloads.

For each case, record a discarded warmup of at least 250 ms and three operations,
then nine batches of at least 100 ms and three operations each. Discard the first
two batches by declaration, retaining seven. Each batch reports mean original timed
work per operation, operation count, raw durations and total wall time. Compare
capture minima of these seven batch means; do not call them individual-call latency.
Validate full output after every operation outside its original timed interval.

Run the existing scheduling cases separately with the original ticker and single
operations: seven samples per case per capture, both engines, paired ABBA/BAAB blocks. Compare
scheduling metrics descriptively, not with the throughput ratio rule. Include
empty/tiny/large sources and empty members, preserving existing budget and lifecycle
test evidence. Record ticks before exhaustion, maximum items between ticks, maximum
and p99 observed gaps, including the final gap. A baseline starvation result is
expected evidence, not a reason to drop a row. No warmed throughput result qualifies
scheduling, and no observed wall-clock gap establishes a hard preemption bound.
The current harness needs a latency-only selection to avoid rerunning throughput.
Explicitly disposition the previously reviewed 2–3.5% small-item bookkeeping cost
even if the new result remains below 5%; do not claim zero overhead. That earlier
figure is reviewer evidence on a loaded host, not qualification.

## G06: long-line scaling and short-line controls

Compare cea195d with 16af1dc, both engines, all 175 cases from the existing G06
matrix, using a common committed measurement harness. Run timing separately from
resource instrumentation. Preserve the established structural/allocation evidence.

Add optional timing warmup/batching to the G06 harness before freezing it: same
250 ms/three-operation warmup and nine 100 ms/three-operation batches, first two
discarded, seven retained. Reuse prebuilt fixtures and preserve each operation's
original open/validation timing boundary. Defaults and resource mode stay unchanged.
Keep the complete matrix and budget separate execution windows for stdlib G06 and
zlib-ng G06; do not promise G06–G08 in one night. Reviewer planning estimates are
4–9 minutes per G06 capture, or roughly 72–162 minutes for 16 retained plus two
warmup captures per engine, before host deferrals. These are estimates, not measured
runtimes. Allow a four-hour window per G06 engine, at most one complete attempt,
and reserve at least three hours for measurements. Record elapsed wall time after
each capture and defer unfinished work at the cutoff; never reduce cases to fit.
A window deferred before any block starts produces no series, and needs a new
authorized window rather than an automatic reschedule. A cutoff during a block
retains but rejects that block and records the remaining blocks as unstarted.
Allow one separately scheduled continuation to run the unstarted blocks with the
same pins and protocol; do not replay completed blocks or the cutoff block. Keep
window boundaries explicit in analysis. This completes the original series, not
the one follow-up allowance. If still incomplete after that continuation, stop for
an explicit disposition; do not roll forward indefinitely. The one follow-up series
is available after all four block slots have completed or been rejected.

G08 and G07 get their own bounded manifests/windows. A slower observed duty cycle
requires a revised future schedule, retaining the incomplete attempt.

Record raw operation timings and wall duration so short-line controls have enough
measurement work without disguising setup cost.

Report baseline/candidate ratios for every case and size-doubling ratios within
matched encoding, newline, content and chunk-size families. Keep fast-path short-line
controls distinct from generic long-line cases. Do not infer a universal time
complexity from a few sizes; connect timings to the already-measured work counts.

## G07: first-result latency and scheduling

Retain candidate 16af1dc, both engines and the complete 104-case matrix. G07 requires
measured behavior and disposition, not a manufactured speedup comparison: there is
no partial-read production optimization being qualified. Collect seven independent
fresh-process samples per case, preserving original setup and timer boundaries.
Run engines in alternating order over seven rounds, one sample per case per round,
instead of seven consecutive repeats for one engine. No batching, discarded early
calls or added CPU pre-spin. This is first-read latency after the harness's normal
fixture/open setup, not cold-boot latency or a controlled idle-core measurement.
Fixture creation can involve substantial gzip compression on that same core before
the first read. Label all results single-core pinned: executor threads and the
four-handle cases share CPU 13 and measure time-slicing, not multicore throughput.
The same affinity limit applies to G08 offloaded work on both comparison sides.

Report all samples, median, minimum and maximum first-result/EOF/error times,
ticker progress and gaps, grouped by fixture, read API, seekability and size limit.
Preserve distinctions between partial output, eager validation failure and EOF.
Pair the timing observations with the existing read-ahead, allocation and limit
results. Document variability and the retained eager-drain tradeoff. If an anomalous
case needs repetition, retain the initial result and declare the follow-up scope.

## Analysis and disposition

For G06/G08 throughput, let A1/A2 and B1/B2 be the two capture minima per block.
Record the block ratio `sqrt(B1*B2 / (A1*A2))`, and within-version drift
`max(t1,t2)/min(t1,t2)-1` for each source. Report all four block ratios, their median,
and both baseline and candidate drift; do not pool all samples and select the
single fastest observation. This balances order but cannot eliminate nonlinear drift.

Screen each block separately: it is usable for an effect claim only when both
within-version drifts are at most 2%. A row needs at least three of four usable
blocks; report all four ratios and the all-block median regardless. Do not silently
omit the fourth block or pool selected samples. Require agreement in the direction
of any claimed effect among the usable blocks; contradictory/noisy evidence is
inconclusive. ABBA spaces A farther apart than B; BAAB reverses that spacing, so
report order and both drifts rather than treating them as equal-duration probes.

Investigate every all-block median slowdown above the plan's 5% threshold even if
noisy; noise does not excuse a potential regression. A slowdown above 5%, exceeding
twice the largest within-block drift and present in at least three of four blocks,
is stronger evidence requiring targeted investigation and written disposition.
Mixed signs or effects comparable to drift do not support an improvement claim.
There are hundreds of rows: a single threshold excursion is an investigation
trigger, not a statistically established finding. These are operational screens,
not confidence intervals or proof that a smaller effect is absent.

Allow at most one independent follow-up series for inconclusive rows, using the
same four-block protocol and retaining both series. For G06 rerun the entire matched
size family so doubling comparisons remain intact; freeze the selected family/case
list before follow-up. Report the initial and follow-up outcomes separately, and
require an explicit explanation of any disagreement. Do not select the better series
or call a row resolved solely because the second series is faster. A row still
inconclusive after follow-up needs an explicit maintainer disposition or leaves its
gate open. There is no quota of unresolved rows that silently passes the gate.

G07 is descriptive, so do not apply this throughput ratio rule to it. Qualification
requires reviewing its timing distributions with scheduling/resource behavior and
recording limitations. G08 likewise needs the separate fairness evidence, not just
a throughput threshold. G09/C0 follows reviewed G06–G08 results; G17 remains a
separate release-wide qualification. A completed service never closes a gate itself.

## Implementation and review boundaries

1. Archive diagnostic/deferred results and review this protocol (documentation only).
2. Implement and test optional G06 batching and G08 latency-only selection, plus a
   comparison report that labels noisy rows inconclusive. Preserve default behavior.
3. Settle the concrete host policy/window, implement the bounded runner changes,
   commit after full tests and all-file prek, then freeze and review new manifests.
4. Collect results sequentially from clean commits, review evidence, and disposition
   each gate. Do not retrofit the old manifests or rewrite unsuccessful attempts.

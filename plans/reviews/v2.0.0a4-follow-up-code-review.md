## Findings

### 1. Derived output-name collisions

Distinct source names could derive the same staged output. For example,
noncanonical names and case-only differences could overwrite one partition
while the manifest still described two successful shards.

Correction:

- accept only nonempty `<partition>.jsonl.gz` input names;
- derive output names during preflight validation; and
- reject NFC-normalized, case-folded output-name collisions before staging.

### 2. Repeated cancellation detached cleanup

The original `await asyncio.shield(_cleanup_staging(...))` created an implicit
task. A second cancellation could interrupt the outer await while cleanup kept
running after `ingest_dataset()` returned.

Correction: create an explicit cleanup task, shield it from each finite outer
cancellation request, and inspect its result only after it reaches a terminal
state. The original ingest exception remains primary and cleanup failures are
still attached as notes.

### 3. Publication did not atomically refuse an existing destination

The existence check and `Path.rename()` were separate. POSIX directory rename
can replace an empty directory created in that window.

Correction: publish with the platform's atomic no-replace primitive:

- Linux `renameat2(RENAME_NOREPLACE)`;
- macOS `renamex_np(RENAME_EXCL)`; and
- Windows `Path.rename()`, whose native behavior refuses an existing target.

A Linux libc without `renameat2` fails closed with `ENOTSUP`. A filesystem
without `RENAME_NOREPLACE` support fails closed with its native error, commonly
`EINVAL`; neither case falls back to replacement semantics.

### 4. Early staging initialization leaked the partial directory

Creating `partitions/` occurred before the cleanup-protected block. An injected
directory-creation failure left the unique partial directory behind.

Correction: staging creation and initialization now occur inside the same
cleanup scope as ingest, manifest generation, and publication.

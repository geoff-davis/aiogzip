# WP5 September 30: fresh WP5 comparison with fallback windows

The maintainer authorized the fresh G08 stdlib comparison of unchanged WP5 f73ae8d
with committed candidate 2f78925 for the night of September 30. They also
authorized up to three start times, to reduce the chance that one burst of host
activity ends the night without a series. G08 remains open, and no gate closes
unattended.

## Design

Three one-off windows start just after the quarter-hour ZFS snapshot and well
clear of the hourly backup. The two fallbacks run only when every earlier window
ended without starting a series.

| Window | Pacific time | Runs when |
| --- | --- | --- |
| a | 02:15:30–03:10:00 | always |
| b | 03:15:30–04:10:00 | window a never initialized, or deferred with every block unstarted |
| c | 04:15:30–06:00:00 | the same holds for both a and b |

At most one series can exist. Once any window starts a block, later windows skip,
even if that series is incomplete. No window chooses between series, replays a
rejected block, or continues a partial one. A deferral before any block starts
produces no series, so a fallback is a new initial series, as in the
[draft record](v2.0.0b2-wp5-g08-stdlib-wp5-draft.md).

This is a bounded, tonight-only exception to the rule that each further window
needs review first. The maintainer authorized all three attempts in advance.
They are not an open-ended retry mechanism. A started, failed, incomplete or
unreadable attempt still prevents any fallback.

The start times follow the [September 29 review](v2.0.0b2-wp5-nightly-20260929-results.md).
Sanoid takes frequent snapshots at :00, :15, :30 and :45, with lighter runs every
five minutes. Syncoid runs hourly with up to five minutes' randomized delay. A
clean series needs about 12.5–13.5 minutes including the mandatory 120-second
quiet preflight; the September 28 series took 13.5 minutes from service start.
Starting at :15:30, it would end around :28–:29, just before the :30 snapshot,
and only if the preflight passes at once. Any reset of the quiet period pushes
it into :30. This is correlation-based placement, not a proven quiet interval.
Any window may still defer or reject blocks.

## Fallback condition

Windows b and c use a systemd `ExecCondition` with
`scripts/check_b2_prior_windows.py`, frozen byte-identically as
`scheduled/check_b2_prior_windows-20260930.py` (SHA-256 `ad9c2fc5…`). It exits 0,
permitting the fallback, only when each earlier output directory either doesn't
exist or holds a `status.json` with status `deferred`, block slots exactly
matching the block IDs of the manifest the runner embeds in that status, and
every slot `unstarted` with an empty capture list. Any other status, a started block, or a missing or
unreadable status skips the fallback. A skip is logged in the journal and creates
no result directory. The runner creates its output directory before any command,
so an absent directory means that window measured nothing.

A deferral during warmups qualifies: warmups are discarded captures, and the
series only starts with the first block. `tests/test_b2_prior_windows.py`
covers:

- an absent earlier output, and a deferral including an interrupted warmup;
- `complete`, `incomplete`, `failed` and `running` statuses;
- rejected, complete and capture-bearing blocks;
- empty, non-list, truncated, extra and reordered block slots, missing declared
  slots, and non-list capture fields;
- missing, malformed and incomplete status files;
- the command-line exit codes and absolute-path requirement.

# aiogzip 2.0.0a3 small-write disposition

## Decision

The `2.0.0a3` candidate improves the extreme 10-byte write diagnostic over
`2.0.0a2`, and no measured write size is more than 5% slower than `2.0.0a2` on
either engine. It does **not** restore `v1.11.0` performance for every
representative write size, and this record does not claim that the regression
is fixed.

The remaining cost is the per-call ownership and failure-boundary protocol
introduced by the provisional 2.0 codec. Preserving that protocol is a fixed
release decision: each `write()` snapshots its input, owns one reserved codec
operation, drains all output from that operation, reports its own sink failure,
and advances the file position only after the sink accepts the output. The
profile shows that removing enough of this work to reach 1.x parity would
require weakening those semantics or adding cross-call buffering.

The 10-byte miss is non-blocking under the plan because the candidate is faster
than `2.0.0a2`, passes the hard anti-regression gate, and parity with 1.x is not
a blocker when it requires changing the frozen write contract. The historical
1 KiB through 64 KiB gate does require the plan's specific independently
reviewed exception for the rows called out below. This document supplies the
profile evidence for that maintainer decision; it does not record independent
approval.

## Safe optimization results

Retained changes:

1. Exact `bytes` inputs bypass redundant bytes-like coercion while every other
   accepted object, including a `bytes` subclass, still takes the raw-buffer
   snapshot path before asynchronous work.
2. The binary file commits its position with one addition only after all codec
   output has reached the sink.
3. The synchronous operation iterator inlines the ownership and poisoning
   checks formerly reached through another Python frame. The async driver keeps
   its existing cancellation path.
4. The encoder's already-snapshotted private feed entry inlines its state and
   strict-size checks before reserving the operation.

Contract tests cover bytes-like snapshotting, input length returns, position
commit timing, short/invalid/zero-progress sink counts, triggering-call errors,
cancellation and poisoning, broken close behavior, distinct flush semantics,
bounded `writelines()` behavior, iterator/coercion failures, and abandoned
operation cleanup.

A specialized Python iterator for encoder feeds was implemented and measured,
then reverted because it made representative tiny writes approximately 14–20%
slower. Cross-call buffering, deferred sink errors, background tasks,
unreserved generator access, and changed output metadata were not attempted
because the release plan forbids their semantic changes.

## Batching alternatives

The candidate matrix compared identical logical records using repeated
`write()`, `writelines()`, and explicit 64 KiB and 256 KiB application batches.
Representative medians:

| Engine | Record size | repeated `write()` | `writelines()` | 64 KiB batches | 256 KiB batches |
| --- | ---: | ---: | ---: | ---: | ---: |
| stdlib | 10 B | 0.7383 | 0.1039 | 0.0114 | 0.0132 |
| stdlib | 1 KiB | 0.0212 | 0.0145 | 0.0122 | 0.0122 |
| stdlib | 64 KiB | 0.1142 | 0.1181 | 0.1145 | 0.1179 |
| zlib-ng | 10 B | 0.7059 | 0.0873 | 0.0014 | 0.0025 |
| zlib-ng | 1 KiB | 0.0084 | 0.0037 | 0.0015 | 0.0025 |
| zlib-ng | 64 KiB | 0.0866 | 0.0903 | 0.0884 | 0.0915 |

`writelines()` is the supported bounded batching API when one failure boundary
per record is unnecessary. Applications that assemble records asynchronously
can aggregate roughly 64 KiB before `write()`; a 256 KiB batch was not better on
this workload. Neither alternative is represented as semantically equivalent
to one awaited `write()` per record.

Fixed-aggregate concurrent memory runs with one, four, and ten independent
writers remained close: stdlib 10-byte medians were 0.706, 0.715, and 0.738 s;
zlib-ng medians were 0.709, 0.691, and 0.708 s. Path-backed 10-byte medians were
0.732 s and 0.707 s, respectively, close to the memory sink. This confirms that
the per-call protocol, not file I/O or single-stream contention, dominates.
Allocation samples and complete path/concurrency correctness records are in
[`v2.0.0a3-wp4-write-surfaces-stdlib.json`](data/v2.0.0a3-wp4-write-surfaces-stdlib.json)
(`96fe4493...c764`) and
[`v2.0.0a3-wp4-write-surfaces-zlib-ng.json`](data/v2.0.0a3-wp4-write-surfaces-zlib-ng.json)
(`e0d5a612...6752`).

## Preserved semantics and future direction

No public write semantic changed. In particular, each call retains its own
immutable snapshot, operation reservation, compressed-output drain, sink-error
boundary, position commit, cancellation poisoning, and broken-member close
behavior. `flush()` remains an explicit compressor flush rather than an
ordinary write.

If workloads need both a convenient per-record interface and batching-level
throughput, a future explicit buffered-writer API could make the changed error
and durability boundaries visible in its name and contract. Such an API would
need a bounded byte limit, explicit `drain()`/`flush()` behavior, deterministic
error attribution, cancellation rules, and close semantics. It must not become
the default `write()` behavior during this release.

## Overlap-guard follow-up

Review identified a narrow unsupported-concurrency window after an offloaded
operation released its codec token but before its task published the new file
position. Commit `4c994aa3b80776aeb495cc57668591af3eaa3603` moved the
ledger consistency check before operation reservation. A call entering that
window is now rejected without reserving work or poisoning the member; the
owning task then publishes the position normally. A deterministic event-based
test covers the ordering and proves a later sequential write remains usable.

## Final dead-check removal

Once the pre-reservation overlap guard was in place, review proved that no
supported path could change `encoder.input_size` between operation drain and
position publication. Commit `8a2e59f179f0ed3cea1a5c90d00ac766768626e2`
removed that redundant post-drain property read and branch. Position still
derives from the authoritative pre-operation encoder ledger plus the accepted
snapshot length, and failures still publish no new position.

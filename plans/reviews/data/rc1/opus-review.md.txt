### RC1-01 — Failed or cancelled text `seek()` leaves stale text over a moved binary position; subsequent reads silently return corrupted data
- **Category:** RC1-blocker · **Severity:** high · **Confidence:** high (reproduced deterministically)
- **Evidence:**
  - `_text.py:557-606`: cookie path awaits `self._binary_file.seek(origin_offset)` (~l.591) and only *afterwards* resets decoder/buffer/origin; no exception/cancellation handling in between.
  - `_seek_to_plain_position` (`_text.py:948-1009`) replays/decodes and only at the end clears `_text_buffer` and sets the origin (l.1003-1009); a failure/cancel mid-way leaves the old buffer + origin.
  - Binary layer reports its new position and remains HEALTHY ("Failure after rewind has already occurred: report post-rewind position" — state-model doc row at line 419 covers binary only).
  - The text-origin transition table (state model l.205-219) has no row for a failed/cancelled text seek — the model is silent.
- **Repro 1 (cookie seek, transient no-effect source failure — r1):** 400 lines, read 30 lines, `tell()`, read 40 more, make next source read fail, `seek(cookie)` → OSError. Afterwards binary position 0, health HEALTHY; `read()` returns `'lineline 0000\nline 0001...'` instead of `'line 0030\n...'`.
- **Repro 2 (forward plain seek — r2):** next line returned is a stale fragment `'00003 35bf9a…'` followed by `'00017 …'` — lines 3–16 silently skipped.
- **Repro 3 (cancellation, ordinary API):** r4 (custom source, cancel `seek(cookie)` after 0.5-2 ms) → `'lineline 0000…'` / `'line0\nline 0011…'`, HEALTHY. r5 (real on-disk file opened by path, native aiofiles, 200k lines, `chunk_size=4096`): read 5 lines, start `seek(40*150000)`, cancel after 0.5–20 ms, `read(8000)` returns the stale buffered lines 5.. then jumps directly to wherever binary stopped — malformed/non-contiguous output, no indication. So `async with asyncio.timeout(...): await f.seek(...)` on an ordinary file can silently lose data.
- **Not a b2 regression:** identical results on v2.0.0b1 and v1.11.0 for r1/r2.
- **Why the stateful harness misses it:** `tests/stateful/model.py:875-890` `handle_error` for a failed text seek assumes "rewind_ok → position 0" then calls `widen()`; text payloads are ≤3000 chars (`generator.py:376`) and there is no cancel-during-seek-with-replay event.
- **Suggested fix (no public API change):** In `AsyncGzipTextFile.seek` wrap the binary seek + replay in `try/except BaseException`: on any exception, invalidate text state before re-raising — clear `_text_buffer`/pending lines, reset decoder, and either (a) mark text poisoned (`_read_poison_seen` / `_read_poisoned`) so reads refuse until `seek(0)` (preferred; matches BC2/BC10 semantics and `seek(0)` recovery is already guaranteed), or (b) re-anchor origin to the binary layer's reported position with a fresh decoder (only valid if that position is a character boundary — riskier). Same in `_seek_to_plain_position`: clear buffer *before* replay, not after. Add a state-model row and a ledger entry (BC11) since post-failure behavior changes from "wrong data" to "refusal until seek(0)".
- **Test:** parametrize r1/r2/r4 over cookie and plain targets × {no-effect failure, consumed failure, cancellation, decompression limit}; assert the next read either returns the exact correct continuation or raises — never wrong text. Add native-file cancellation test (r5 style). Add a "cancel during seek_mark / seek_abs" event to the stateful generator with payloads > one chunk; tighten `model.handle_error` so a failed text seek demands refusal or exact content instead of `widen()`.

### RC1-02 — `inspect()`/`verify()` open the file themselves, bypassing BC3 open settlement and native-call settlement
- **Category:** should-fix-before-RC1 · **Severity:** medium · **Confidence:** medium (code path certain; leak not reproduced — timing dependent)
- **Evidence:** `_inspection.py:55` `source = await aiofiles.open(filename, "rb")` and `_inspection.py:69` `await source.read(chunk_size)` directly — not through `_opening._acquire_path` / BC3's settled open, nor through `_source_io._NativeSourceCall`.
- **Failure scenario:** cancel `inspect(path)` while aiofiles' executor `open()` is running → the thread's file object is never returned/closed (the BC3/F3 "ownerless resource" class b2 fixed for `AsyncGzipFile`, not here). Cancel during a native `read`: closing the source can run while the executor read is still active (BC1/BC9 class). Existing test (`tests/test_inspection.py:553`) only covers a source that raises CancelledError synchronously.
- **Fix:** reuse `_acquire_path` (or its settlement helper) for the open, and route reads through the same native-call settlement the binary reader uses.
- **Test:** gated-executor fixture (as in `tests/stateful/interpreter.py` Gate/GatedExecutor): park the open / a read, cancel, assert no live FD and no close-before-settle.

### RC1-06 — Abort-path cancellation count can leak when a custom source does not raise CancelledError
- **Category:** nice-to-have · **Severity:** low · **Confidence:** medium (code path, not reproduced)
- **Evidence:** `_finish_abort` calls `owner.cancel()` (`_binary.py:2165`); the matching `owner.uncancel()` is consumed only if the owner's call ends in `CancelledError` (`_binary.py:1829-1836`, likewise sink 1917). A custom source that catches CancelledError and returns data or raises OSError (contract violation) leaves the owner task's `cancelling()` count at 1; an enclosing `asyncio.timeout()`/TaskGroup in that task can then misclassify a later timeout as external cancellation (TimeoutError → CancelledError).
- **Fix:** in `_call_custom_source`/`_call_custom_sink`, when `_source_abort_requested` is set and the call completes/fails without CancelledError, still `uncancel()` once in `finally`.
- **Test:** source that swallows cancellation, inside `asyncio.timeout`; assert `current_task().cancelling() == 0` after the context exit.

### RC1-07 — Context-exit abort silently swallows secondary errors

### Disagreement with a known item (labelled)
On the Windows seed-734 timeout: agree with the disposition, but RC1-01 shows the stateful model's `widen()` after a failed seek (`model.py:875-890`) is too permissive — it doesn't check data-loss outcomes there. Recommend tightening it as part of RC1-01, not separately.

### Overall assessment
The codec, binary reader, settlement and ownership machinery are careful, well tested, and documented in detail; I found no new defect in `codec.py`, `_codec_async.py`, `_source_io.py`, or the binary health model. The codebase is **ready to start RC1 work once RC1-01 is addressed** — it is a silent data-corruption path reachable with an ordinary on-disk file and `asyncio.timeout` around a text `seek()`. It predates b2, but an RC should not ship with it, and it is privately fixable (poison/re-anchor text state on seek failure plus a ledger entry).

**Top three:**
1. **RC1-01** — make text seek failure/cancellation invalidate text state; tighten the stateful model to catch it.
2. **RC1-02** — give `inspect()`/`verify()` the same BC3 open and native-read settlement.
3. **RC1-04 + RC1-03** — make the published artifacts provably the attested ones and pin all workflow actions exactly (plus the RC1-05 3.14 Windows/macOS legs before tagging rc1).

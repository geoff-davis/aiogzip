### Pinned inputs

Nothing in a run is supplied at launch except `MODE`.

- **Units.** Each run is a systemd user unit started manually. The unit's
  `ExecStartPre` lines check the sha256 of its driver (`run.sh` or
  `preflight.sh`) and of `harness.sha256`.
- **Driver checks.** The driver refuses to start unless
  `sha256sum --check --strict harness.sha256` passes. That list pins
  `quiet_gate.py`, `summarize.py`, `envcheck.py`, both structural step lists
  and every manifest.
- **Manifests.** `manifest-<mode>.json` is the only source of commits,
  roles, the runner commit, the categories, the runner's `benchmarks/` and
  `scripts/` tree hashes, the `uv.lock` sha256 and the installed-environment
  fingerprint. There are no environment overrides.

### Environment comparability

Every run checks the shared venv twice:

- `uv sync --locked --all-extras --check` must find it in sync with the
  pinned lock;
- `envcheck.py` must reproduce the pinned fingerprint, a sha256 over the
  interpreter version, build and resolved paths and every installed
  distribution's version.

The A/A window and the final windows therefore run against one proven
environment. The venv also carries a stale `aiogzip 1.9.1` dist-info beside
the editable install. It is part of the fingerprint, and `--source-root`
imports are verified per capture, so it cannot be measured instead.

The fixtures fall into three groups:

- The write fixtures are deterministic, and their identities (sha256 per
  size) are frozen by the preflight and checked in every capture.
- Every runner and structural payload comes from a seeded or fixed
  generator in the pinned trees, so both sides of every window measure the
  same bytes (plan §15.1). `DataGenerator.generate_binary()`, which the
  `io`, `concurrency`, `memory`, `compression` and `inspection` benchmarks
  use, drew from `os.urandom` until `9ae439b`; it now draws from
  `random.Random(0)`, equally incompressible. Gzip fixtures that a capture
  compresses at run time may differ only in their header `mtime`.
- Where structural rows carry fixture digests, the frozen row signatures
  include them.

### Execution

- **Worktrees.** The driver creates fresh detached worktrees for A, B and
  the runner. A and B are separate even when they share a commit. It
  verifies each commit and a clean tree, the runner's tree hashes, and both
  `uv.lock` copies.
- **Interpreter.** Every step runs the venv's interpreter directly, with
  stdin closed, so nothing re-syncs the venv mid-window.
- **CPU and quiet gate.** Every step is pinned to CPU 13. The WP9 quiet gate
  must see 120 s at 2.5 foreign cores or fewer, and a monitor samples
  foreign CPU every 5 s throughout.
- **Captures.** For each engine (stdlib, then zlib-ng), eight captures run
  in ABBA ABBA order. Each capture runs two steps:
  1. `run_benchmarks.py --category io,micro,concurrency,memory,regressions,read_health,text_origin --repeat 5 --regression-profile quick --regression-mode throughput`
  2. `bench_a3_regressions.py --categories writes --repeat 5` with the
     default sizes (10 B to 256 KiB) and all four write methods.
- **Structural steps.** In the C0 and WP0 windows, these run after the ABBA
  loop, once per side and engine: A then B on stdlib, B then A on zlib-ng.

## Statistics and decision rule

`summarize.py window` refuses any window in which:

- a capture or structural output is missing, incomplete, failed or
  mislabeled;
- a commit, the runner (harness) commit, the requested or active engine or
  the clean state is wrong; structural outputs are checked from their own
  provenance fields;
- a runner capture's row set, including duplicate rows, differs from the
  set the preflight froze for that role and engine;
- a write capture's fixtures differ from the frozen ones, or a write result
  is not `ok` with five samples;
- a structural output's row signature differs from the frozen one. The
  signature is each row's shape at every depth: keys, strings, Booleans,
  nulls and list structure, including lengths. Only measurements are
  replaced: each number by its type name, and each non-empty list made only
  of numbers by its element types, because timed-budget batches
  (`operation_seconds`) vary in length;
- a runner duration or write median is not a finite positive number, or a
  `memory` row lacks a finite `memory_increase_mb`;
- foreign-CPU samples fail to cover any capture or structural step
  continuously;
- foreign CPU exceeds 2.5 cores during any capture or step.

A refused window is rerun whole. The candidate is never rerun alone.

The primary statistic is each benchmark's minimum of the four capture medians
on each side, as in CLAUDE.md method A. The four adjacent A/B pair deltas are
reported alongside it.

Plan §15.1 policy applies to every runner row and write row of the C0 and WP0
windows:

| Slowdown (B against A, by minimum) | Required action |
| --- | --- |
| 5% or less | None |
| More than 5% | Investigation and a recorded disposition |
| More than 10% and attributable to the candidate | Blocks by default |

Adjacent pair deltas inform stability but do not decide eligibility.

**A/A use.** The A/A window reports each row's delta and the largest absolute
delta per engine. A final-window row above 5% is still investigated even if
its A/A row was also above 5%. The A/A result is evidence within that
investigation, not a waiver.

The `memory` category records an RSS increase per capture. It is reported
per capture and judged with the G07 resource rows, not by percentage.

## Structural steps and their criteria

Each step is judged against the criterion recorded when its gate closed, and
the record cites that criterion per row. None of these scripts emits a
pass/fail field. Each raises on a correctness failure, and its numbers are
judged as below.

Where a gate closed with non-default options, the step uses those options so
that the criterion applies unchanged.

| Step | Options | Gate criterion | Judged from |
| --- | --- | --- | --- |

| `g03-source-reads` | default (`--repeats 11`) | Source correctness; timing provisional ([WP2](v2.0.0b2-wp2-completion.md)) | The script's output-equality assertion. ## Preflight (needs authorization; not evidence)

`preflight.sh` runs as `aiogzip-g17-preflight.service` (`RuntimeMaxSec=3h`).
It has the same pinned inputs and environment checks as a window. It covers
three roots (`c0`, `wp0` and `candidate`, which is the runner commit) on
both engines. Per root and engine it runs:

- the runner categories once (`--repeat 1`);
- the write sizes once;
- every `structural-c0.txt` step once, with its registered options.

It runs unpinned and with no quiet gate, and its output goes to
`.cache/wp10-bench/preflight-<time>/`. It is never cited as timing evidence.

Its results serve three purposes:

- **Durations** per step set each window's `RuntimeMaxSec`.
- **Compatibility:** any step that fails on a root, notably `read_health`
  and `text_origin` on `dc8950c`, which postdate it but use only the public
  API.
- **Frozen row sets.** `summarize.py preflight` validates every output's
  provenance and writes `expected-rows.json`, the per-role and per-engine
  runner row set, write fixtures and structural row signatures. It notes any
  role whose rows differ from C0's.

An amendment follows the preflight and is reviewed before the A/A window. It
records:

- the durations;
- any incompatibility, with a `manifest-wp0.json` category change if
  needed;
- the hash of `expected-rows.json`;
- the regenerated `harness.sha256`;
- `aiogzip-g17-aa.service`, with its pinned hashes and runtime limit.
